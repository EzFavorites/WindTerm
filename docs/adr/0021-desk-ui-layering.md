# ADR-0021 · desk 渲染分五个环，换框架的成本压在渲染层与平台层

- 状态：已采纳
- 关系：不改动任何既有边界，只把 `apps/desktop` 内部再分一层，并为「换 UI 框架」定出接缝与成本

## 背景

需要为「以后可能对 egui 不满意、换一个框架」预留接缝，而不是等真换的时候再拆。

现状盘点支撑三件事：

1. `ui/` 下多数文件直接引用 `egui`，但已有少数文件做到了数据与画法分离（设置页、会话表单、文件面板、日志等）。这条路在本仓库走得通，不是空想。
2. `ui/` 之外的 egui 触点集中在窗口、字体、剪贴板、主题、抓屏——正是「渲染后端」该待的地方，只是还没被命名。另有若干一次性实验二进制也引用 egui，但它们被版本控制忽略，干净检出里不存在，因此不算触点，也不进白名单。
3. 上层已经干净：`term-core`（值类型与终端语义）与 `term-app`（动作、reduce、视图状态、效果值）都是零 UI 依赖，由依赖表检查守着。换框架时这两层一行都不用改——这是本项目最值钱的存量。

## 决策

### 1) 五个环，每环一个职责

```
R4  platform   窗口 / 字体 / 剪贴板 / 主题 / 抓屏     egui、eframe 只允许出现在这里
      ↑ 只被 R3 调用
R3  render     把「画什么」翻译成后端调用             egui 的 Ui / Painter / Response
      ↑ 只读 R2 产物，不自己算
R2  view       纯函数：状态 + 快照 + 尺寸预算 → 视图模型    零 egui，可单测，可序列化
      ↑ 只读 R1
R1  app        动作 / reduce / 视图状态 / 效果值       term-app，零 UI
      ↑
R0  core       值类型与终端语义                       term-core，零 UI
```

**R2 是本 ADR 唯一新增的层。** R0 与 R1 已存在并有门禁；R4 事实上存在（窗口、字体那几个文件）只是没命名；R3 就是今天的 `ui/`。

### 2) R2 的产出契约（决定它是否值得存在）

R2 只产出四类东西，多一类都算越界：

| 类型 | 内容 | 为什么允许 |
|---|---|---|
| 文本片段 | `(文本, 样式角色)`，角色是 `Label` / `Value` / `Muted` / `Accent` 这类**语义名**，不是颜色值 | 换主题或换框架时，只需换一张角色映射表 |
| 矩形 | 相对容器的位置与尺寸（逻辑像素），由布局预算算出 | 让「摆在哪」可单测，不必起窗口比对 |
| 命中区 | `(稳定 id, 矩形, 意图)`，意图是既有动作或命令 ID | 点击分发不依赖后端的 response 对象 |
| 可见项与滚动偏移 | 列表与终端网格的可见窗口（起止行、列范围） | 这是性能与正确性的关键，且是纯算术 |

**不允许出现**：字体句柄、纹理、像素缓冲、`egui::*` 类型、`Response`、动画曲线、事件对象。

判据一句话：**R2 的产物若序列化成 JSON，换到 web 前端应当仍然可用**。做不到，说明它偷偷依赖了后端。

### 3) 换框架的成本矩阵

| 目标框架 | R0 | R1 | R2 | R3 | R4 | 实际要写的 |
|---|---|---|---|---|---|---|
| egui（现状） | — | — | 逐步补齐 | 已有 | 已有 | 0 |
| iced / slint 一类保留式框架 | 0 | 0 | 0 | 重写 | 重写 | 现有渲染文件的等价物 |
| Tauri / web 前端 | 0 | 0 | 0（直接序列化） | 换 TypeScript | 换浏览器 API | 一套前端加一条 JSON 通道 |
| 自绘 / GPU | 0 | 0 | 0 | 重写 | 重写 | 最高，但 R0 / R1 仍不动 |

关键结论：**换框架的真实成本等于 R3 加 R4。** R2 做得越实，换框架时「行为对不对」就越不需要重新验证——因为行为已经在 R2 的单测里钉住了。

### 4) 迁移顺序：只搭顺风车，不做大爆炸

界面本身正在并行重构，此时大规模搬文件只会制造冲突。因此：

1. **立刻生效的规矩**（不改现有代码）：新增或重写一个面板时，数据与画法分文件，纯计算放进 `ui/view/`；`ui/view/` 下不得出现 `egui`；`ui/` 之外引用 `egui` 的文件必须留在白名单内，新增要写理由。
2. **顺手迁移**：哪块面板反正要重写，就把它的行文本、尺寸预算、命中区计算搬进 `ui/view/` 并补单测。一次一块，不追求覆盖率。
3. **暂停判据**：搬完三块（建议顺序：状态栏 → 终端留白 → 菜单）后停下来评估——若 R2 的产物确实被 R3 干净消费就继续；若 R2 里开始出现「怎么画」的细节，说明抽象过度，就地收缩。

`ui/view/` 目录在**第一次真实迁移时创建**，现在不建空壳：空模块要么触发未使用代码警告，要么被迫挂一个放宽属性，两者都是噪音。

### 5) 判据

| # | 判据 | 状态 |
|---|---|---|
| V1 | `term-core` / `term-app` 零 `egui` | 已有 |
| V2 | `ui/` 之外引用 `egui` 的文件在白名单内（扫查时排除被版本控制忽略的实验二进制） | 新增 |
| V3 | `ui/view/` 零 `egui` | 目录建立时加 |
| V4 | `ui/render/` 之外零 `egui` | 迁移过半后再收紧 |

把 V4 留到后面不是拖延：**门禁的价值在于它始终是绿的**。一条从第一天就有上百个例外的规则，等于没有规则。

## 后果

- **正面**：换框架的成本被限定在 R3 与 R4，行为正确性由 R2 单测兜底；`ui/` 之外的 egui 触点被白名单钉住，防止逻辑层偷偷耦合渲染层；新代码有明确落位规则——数据进 `view/`，画法进 `render`。
- **负面**：`ui/view/` 会在相当长时间里只有零星几个模块，看起来「没做成」。这是刻意的：它随重写生长，不靠一次性搬迁。
- **风险**：R2 抽象过度，演变成两套 UI 代码。缓解是四类产物白名单加暂停判据。
- **复查触发**：真动手换框架（哪怕只做一次试验）→ 按成本矩阵核对，若 R2 不能直接复用，先修契约再继续；`ui/` 行数继续膨胀或出现巨型单文件 → 说明分层没落地，先做顺手迁移；出现第二个渲染后端（例如同时支持 egui 与 web）→ V4 必须立刻收紧为硬门禁。

### 6) 明确不做

1. **不做 widget trait 抽象，也不做跨框架 DSL 与自绘引擎**。egui 是立即模式，硬抽成保留式组件树等于在本仓库里再造一个小框架，那比换框架更贵；真要自绘是另一个项目。
2. **不为「可能换」提前重写现有渲染代码，也不改 R0 与 R1**。触发条件是「对 egui 的具体不满」（输入法、无障碍、多窗口），不是「抽象不够漂亮」；R0 与 R1 是这套设计里最值钱的部分。

## 备选方案与否决理由

| 方案 | 否决理由 |
|---|---|
| 一次性把所有面板搬进 `ui/view/` | 与正在进行的界面重构冲突；且 R2 契约未经真实消费验证，搬完可能整体推翻 |
| 等真要换框架时再分层 | 那时行为正确性只能靠重新验证，成本无上限；而现在分层的边际成本只是几条落位规矩 |
| 立刻建 `ui/view/` 空目录并加全量门禁 | 空目录产生警告噪音；一条立刻有大量例外的规则守不住任何东西 |
| 直接跳到 web 前端（Tauri 一类） | 当前没有对 egui 的具体不满作为触发条件；而且 R2 未成型时换，等于把行为验证成本一次性付清 |
| 让 R2 直接产出 egui 的 `Response` 与样式对象 | 那就把后端类型焊进了「纯函数」层，换框架时 R2 要跟着重写，分层失去意义 |
