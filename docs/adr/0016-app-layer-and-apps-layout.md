# ADR-0016 · 应用层独立成 term-app，可执行目标进 apps/

- 状态：已采纳（其中「两个可执行目标」条款已由 ADR-0020 取代；其余继续有效）

## 背景

此前仓库是「一个可执行目标加三个编译单元」：动作层与投影同处一个 bin crate。三个压力点促成拆分：

| 压力 | 具体表现 |
|---|---|
| 动作层没有自己的名字 | 「按下复制之后该发生什么」写在可执行目标内部。它不依赖 UI，但只有打开那个 bin 才找得到；别的入口想复用，只能复制一份 |
| 「动作层不得依赖 UI」只是检查规则 | 门禁用 grep 守着这条约定，新增一行 UI 引用只要没人跑脚本也能通过；依赖表则根本编不过 |
| 第二个可执行目标无处落脚 | 无窗口模式只是桌面端的一个开关。环境体检、能力面清单、跑一条命令并拿到真实退出码，都得靠起窗口间接完成，或另写一套逻辑 |

## 决策

### 1) 目录

```
crates/term-core     纯语义（不变）
crates/term-runtime  副作用会话（不变）
crates/term-app     新增：无前端的应用层（动作、reducer、视图状态、效果值）
apps/desktop        原可执行目标改名，只留投影        （bin: term-desk）
apps/cli            新增：命令出口                    （bin: term-cli）
```

### 2) 依赖表就是判据

| crate / app | 允许依赖 | 被依赖表挡住的东西 |
|---|---|---|
| `term-core` | `vte` / `serde` / `serde_json` | UI、PTY、文件系统、线程、tokio、反向依赖 |
| `term-runtime` | `term-core`、`portable-pty` / `dirs` | UI；反向依赖 `term-app` 与 `apps/*` |
| `term-app` | **只有** `term-core` | UI 框架（拿不到像素）；`term-runtime`（拿不到 PTY、线程、文件系统） |
| `apps/desktop` | `term-app`、`term-runtime`、`egui` / `eframe` | 无（它是唯一允许有像素的地方） |
| `apps/cli` | `term-app`、`term-runtime` | 任何 UI 框架（打印一行字不该拉起窗口） |

`term-app` 的依赖表里没有 `term-runtime`，是本次新增的强约束：应用层拿不到 PTY、线程与文件系统，所以「按下复制之后要写剪贴板」只能以效果值返回，由可执行目标解释。谁想在 reducer 里顺手调用进程或写文件，编译就会失败，而不是靠代码评审发现。

### 3) CLI 的职责边界

`term-cli` 只做**已有能力的文本出口**，不新造语义：

| 子命令 | 回答的问题 | 依赖 |
|---|---|---|
| `doctor` | 这台机器能不能跑（`$SHELL` 可执行、配置目录可写、主题来源、能力面清单、`$TERM`） | 三个 crate 全部 |
| `local exec` | 一条命令在真 PTY 里跑完，屏幕上最后留下什么（不是原始字节流），并透传退出码 | `term-runtime` |
| `session list` | 已保存的会话与分组（读桌面端那份存储） | `term-runtime` |
| `capability` | 能力面清单，`--json` 给脚本，字段名与文档中的口径同名 | `term-app`（唯一判定点） |

`local exec` 的参数语义：按 argv 边界拼回一行 shell 命令，每个参数各自加引号，而不是裸拼接。裸拼接会把 `sh -c 'exit 7'` 变成 `sh -c exit 7`——`sh` 把 `7` 当成 `$0`，退出码变成 0，一个看起来能跑、结果悄悄不对的命令。

## 后果

1. 路径变了：`app/` 迁到 `apps/desktop/`，包名同步改为 `term-desk`，二进制同名。脚本、文档、对账清单里的路径全部跟着改。
2. 多一层：改一个动作要跨两个 crate 看（`term-app` 定语义，`apps/desktop` 解释效果），收益是「谁能碰什么」不再靠记忆。
3. 计数口径变了：此前按 workspace 成员数统计（会把可执行目标也算成 crate），此后按目录数——`crates=3`、`apps=2`。数字看起来变少，含义变对。
4. 复查触发条件：`term-app` 的效果枚举出现只有某个前端才懂的变体（说明分层错位，该把能力与效果一起下移到运行时）；出现第三个可执行目标且大量复制桌面端逻辑（说明抽象放错了层）；单文件超过约五百行（按能力分区继续拆文件，不拆 crate）。

## 备选方案与否决理由

| 方案 | 否决理由 |
|---|---|
| 只加 `apps/cli`，不抽 `term-app` | CLI 要么复制一份 reducer（两套语义会在第一次改行为时分叉），要么依赖 `apps/desktop`（一个可执行目标依赖另一个，在 Cargo 里就是错的） |
| 保留 `app/` 目录名，只加 `apps/cli` | 「`app/` 是 UI 还是应用层」这个名字本身就在误导；改名后「谁有像素」一眼可见 |
| 按协议域切 crate（ssh / sftp / vault 各一个） | 当时没有这些自有实现：SSH 拉起系统 `ssh`，无 SFTP、无隧道、无凭据库，切出来全是转发样板 |
| 让 `term-app` 依赖 `term-runtime` | 等于交出「副作用只能以效果值返回」这条唯一约束，动作层的边界退化成口头约定 |
| CLI 用参数解析框架 | 四个子命令、十来个开关；框架换来一整棵依赖树，并把非法组合的判断藏进派生宏。手写解析顺带让解析结果成为可单测的值类型 |
