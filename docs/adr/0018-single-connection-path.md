# ADR-0018 · 同一会话名只有一条连接路径

- 状态：已采纳

## 背景

会话可以由两个方向打开：界面（带对话框的连接流程）与控制面（脚本、JSON-RPC 桥、无窗口子命令）。两条方向都要建同一种通道，但早期只有界面侧写了连接状态机；控制面遇到内置 SSH 时只能报「需要注入通道」，而没有注入点时最省事的做法是退化成调用系统 `ssh`。

退化的代价不是性能，而是**同一个会话名在不同入口跑出两种行为**：配置写的是内置客户端，实际执行的却是另一个进程；代理、主机密钥策略、认证方式都跟着变。用户复现问题时无法判断走的是哪条路径，日志也对不上。

## 决策

1. **会话名与连接路径一一对应。** 是否使用内置 SSH 由会话配置决定；内置路径失败时不回退到系统 `ssh`，失败就是失败。
2. **通道工厂只能注册一次。** `set_channel_factory` 第二次调用返回错误，不覆盖前一个实现——两个客户端各装一份工厂，等于把分叉留在运行时。
3. **控制面与界面共用同一开会话入口。** 界面自己的对话框只负责交互（问用户名/密码；主机 key 内部自动接受，不再确认指纹），不另建一套连接逻辑；控制面把建通道的逻辑注册成工厂，由同一入口调用。
4. **失败必须可分类。** 未注入通道、需要解锁保险库、网络/主机给不出答案、认证方式不支持，各自有独立错误，调用方能据此提示或拒绝，而不是笼统的「连接失败」。
5. **参数不完整就报错。** 代理配置缺失时报「改会话配置」，不静默直连。

## 后果

- 同一会话名在任何入口行为一致，问题可复现，日志可对照。
- 漏装工厂、漏配代理会暴露成明确错误，而不是「有时能连」。
- 控制面必须先注入工厂才能开内置会话；忘记注入会直接失败——这是有意为之的显式失败。
- 依赖系统 `ssh` 特有能力的配置（例如需要外部 `ProxyCommand` 脚本）必须显式选择非内置模式，不能靠失败回退「碰巧能用」。

## 备选方案与否决理由

- **失败后自动回退系统 `ssh`**：否决。用户看到的是同一会话名两种行为，排障时无法判断实际路径；认证与主机密钥策略也随之改变。
- **允许多次注册、后注册覆盖前者**：否决。把分叉从「失败回退」挪到「运行时覆盖」，问题更隐蔽。
- **界面与控制面各写一套连接逻辑**：否决。两套逻辑必然漂移，最终又回到「同名不同行为」。
