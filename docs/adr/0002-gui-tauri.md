# ADR-0002 · 桌面壳选用 Tauri 2

- 状态：已被取代（被 ADR-0007 取代）

后续演进：WebView 的输入法行为被判定为不可控风险，桌面 UI 改为 egui 原生渲染（ADR-0007）。本文保留当时的决策与理由，其中「为什么不选 Electron、不选纯原生」的论证在 ADR-0007 中继续被复用。

## 背景

需要一套代码覆盖 macOS / Windows / Linux，同时满足：包体小、启动快、能访问原生能力（PTY、串口、钥匙串、菜单栏、托盘、自动更新）。

候选：

- A. Tauri 2：系统 WebView 做前端 + Rust 后端。
- B. Electron：内置 Chromium。
- C. 纯原生：三套平台代码，或单一 Rust GUI 框架。

## 决策

采用 Tauri 2：Rust 侧承担 PTY、SSH、串口、钥匙串等原生能力，前端使用系统 WebView。

### 理由

- **不打包 Chromium**：安装包与空闲内存比 Electron 低一个量级，这直接决定产品是「便携终端」还是「另一个重客户端」。
- **Rust 后端即原生侧**：PTY、SSH、串口、钥匙串都在 Rust 里，经 Tauri command 暴露，不需要 Node 原生插件——这是 Electron 方案最大的工程痛点。
- **原生能力由官方覆盖**：菜单栏、托盘、单实例、自动更新（含签名）、文件对话框、通知都在核心或官方插件内，不必逐个自研。

## 后果

正面：

- 前端可用成熟的 Web 生态（终端组件、组件库、浏览器调试工具）。
- 三平台共享一套 UI 代码。
- 与 ADR-0001（Rust）、ADR-0003（VT 在前端）自然衔接。

负面：

- 三种 WebView 内核（WKWebView / WebView2 / WebKitGTK）行为不一致，只能逐个消化；前端代码因此要写特性检测，而不是按内核版本做假设。
- WKWebView 的输入法行为是已知薄弱点，最终成为推翻本决策的直接原因。
- 无法像 Electron 那样锁定同一个浏览器版本，跨平台差异是长期维护项。
- Linux 侧依赖 WebKitGTK，发行版差异大。

## 备选方案与否决理由

| 方案 | 否决理由 |
|---|---|
| Electron | 包体、冷启动与空闲内存都比系统 WebView 方案高一个量级，与「轻量终端」定位冲突；Node 原生插件（node-pty）的三平台编译是长期负担；该形态已有成熟产品占据，做同构产品缺乏非做不可的理由 |
| 纯原生（三套平台代码） | 三倍工作量，单人不可行 |
| 单一 Rust GUI 框架（egui / iced） | 当时的判断是要自研文本排版、输入法、选区与无障碍，成本过高；该判断在 ADR-0007 中被修正 |
