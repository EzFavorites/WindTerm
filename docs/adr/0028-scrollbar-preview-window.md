# ADR-0028 · 终端悬停预览走「第二条事实窗口」，不复用真实视口通道

- 状态：已采纳（与 ADR-0026 的窗格分组互不影响；不改变真实视口通道的既有契约）

## 背景

指针停在终端滚动条上时，界面给出一块取景框：占满内容区宽度、高度按内容区高度的一个固定比例，框内是历史快照，框外仍是真实视口；框的中心跟随指针纵向位置；预览期间真实视口与滑块都不动，只有真正点击或拖拽之后才滚动。

也就是说，同一帧里界面需要**同时持有两份来自内核的事实窗口**：「用户真实看到的那一屏」与「指针指向的那一屏历史」。

既有通道的形状是「一条上行请求 + 一个下行槽」：

```text
请求范围 → 监管循环收集这一帧的请求 → 每个范围一份屏幕事件
        → 句柄只保留最后一个 → 标签裁切所需范围 → 裁不到即用空白帧
```

关键事实有三条：

- **内核本来就支持一轮吐多份**：请求是列表，切窗口是纯函数，内容版本不因请求递增。瓶颈不在终端内核，而在句柄只有一个槽。
- 标签侧同样只有一份屏幕、一份去重键、一份派生视图。
- 真实视口裁切失败时的兜底是空白帧。

因此，把预览请求直接塞进既有通道，同一帧内两份窗口只有一份能活下来；真实视口拿到预览那份范围时裁切失败，界面就会闪白屏。这是**结构性冲突**，不是偶发竞态。

另一条诱人方案是从已经抓到的真实窗口里裁一段，零接口改动。但最常见的使用状态是贴底，而贴底时根本不发范围请求，手里是旧窗口或空——这个方案恰好在最常用的场景失效。

## 决策

**给预览开一条专用的事实窗口通道，与真实视口通道物理隔离；用「新增变体」而不是「修改既有签名」实现。**

1. 新增预览请求与预览屏幕事件两个变体；既有的范围请求与屏幕事件**签名与语义一字不改**，旧契约保持原样。
2. 句柄增加一个 `preview_screen` 槽；旧事件仍只落进 `screen` 槽；监管循环为预览单独收集一轮请求；终端内核与切窗口逻辑不动。
3. 会话接口增加两个**默认空实现**的方法（请求预览范围、取预览窗口）；测试替身、脚本侧与无头桥接无需改动。
4. 会话池与标签各加一对转发；标签上 `preview_screen` 与 `preview_last_request` 两个字段与 `screen` / `last_request` **并列，绝不共用**。
5. 真实视口的派生链路保持原样；预览图作为独立浮层绘制，直接画已经收到的只读窗口，不参数化正文、叠层与光标绘制，也不改变既有叠层顺序。
6. 纯几何下沉到零依赖模块：滑块位置与滚动位置互算、指针位置换算成历史范围、预览框位置钳制。复用既有视口换算，**不新增第二套行号语义**。
7. 滚动条采用**浮动叠加**而非占位收缩：内容区宽度、列数、终端尺寸都不动，贴底画面保持零差异。代价是滚动条覆盖在网格右缘之上，必须补一条右边界守卫，否则点击滚动条会顺手产生「最后一列」的选区。
8. 预览是**只读**的：不支持在框内选字、查找、点超链接、滚轮。

一句话：把「多窗口」的成本收敛在「槽与去重键的复数化」上，而不是扩散成「全链路多视口」。

### 不变式

1. **预览期间四者不变**：视口位移、真实视图、真实去重键、滑块矩形都不变；只有预览槽与预览去重键在变。这条是整块功能最重要的判据。
2. **两槽互不写入**：真实通道只写 `screen`，预览通道只写 `preview_screen`；裁切永远只看到自己那一份窗口。
3. **底色不透明且取主题背景**：预览框底下是实时视口，半透明底色会让两份画面透叠成重影。
4. **边栏同源**：预览框内的行号边界、时间戳、符号列复用真实终端同一套绘制，配置变化时两边一起变，不各自漂移。
5. **字节视图不画预览**：那是第二套坐标系，也没有屏幕事实窗口；只画滑块、不画预览。
6. **旧去重键仍然只描述真实窗口**：预览的请求与去重是另一对字段，不复用、不交叉判断。

## 后果

正面：

- 结构上排除「预览请求把真实视口挤成空白帧」这一整类问题：两个槽物理隔离，裁切只面对自己的窗口。
- 支持任意历史位置的预览，包括贴底时——预取范围与真实视口的请求互不影响。
- 旧通道的签名、去重键、所有测试替身与无头路径零改动；旧通道的测试仍是回归网。
- 几何层零界面框架、零 IO，可被单测完整覆盖；复用既有换算避免两份行号口径。
- 可逆性高：删掉两个变体、一个槽、两个字段即回到单窗口状态，无数据格式、无持久化、无协议版本影响。

代价（明确认领）：

- 会话接口变宽两个方法；即便有默认实现，这也是「所有实现者都欠一层语义」的口子。当前只有真正带监管者的实现需要覆写。
- 句柄多一个槽、监管循环多一份请求列表、事件分发多一个分支；每帧最多两份屏幕值传递，成本与窗口大小成正比。
- 标签多两个字段，所有构造标签的夹具都要补初始化——机械成本，不是设计成本。
- 预览只读，需要在用户可见的说明里写清，避免被当成「坏了」。
- 浮动叠加要维护右边界守卫；这是用「不改内容区几何」换来的一个小约束。

中性：

- 预览框与滚动条都是叠加层，不参与布局计算；窗口缩放时按内容区重新钳制。
- 预览期间不改变滚动位置，因此「看到某段历史」与「滚到某段历史」是两个动作，符合「先看再决定」的预期。

## 备选方案与否决理由

| 方案 | 否决理由 |
|---|---|
| 复用单槽，从已抓到的真实窗口里裁切 | 贴底时没有范围请求，手里是旧窗口或空，恰在最常见场景失效；也无法覆盖任意历史位置。 |
| 复用既有请求变体，但让两次请求错开帧发送 | 把正确性押在「事件一定分两帧到达」上；输出刷新会让内容版本变化，时序假设随即失效，且这类回归难以复现。凡是能用结构隔离解决的问题，不用时序约定。 |
| 通用多窗口表（请求与事件都带槽标识，句柄存一份槽到窗口的映射） | 架构上更通用，但要改既有请求与事件的签名、所有会话实现、脚本与桥接的替身、通道单测与线上契约。当前只有两个消费者，这是拿全局契约换一个还没出现的需求。**不是错，是早了。** |
| 把标签的派生视图参数化成「任意一份图像」 | 归约、查找、选区、折叠都要开始回答「哪份图像才是权威」，改动从「画一层」膨胀成「双视口全功能」；而真实视图必须只有一个定义，否则查找与渲染会各算一屏。 |
| 预览做成小提示框，只显示若干行文本 | 取景框的意义是「整宽的上下文 + 真实视口仍在框外」，提示框既给不了宽度，也给不了「框外不动」的空间参照。 |
| 预览时临时把真实视口滚过去，看完再滚回来 | 会改动真实滚动位置与去重键，用户失去「我没动、只是看了一眼」的确定感；取消预览时还要恢复一份可能已被输出改变的旧位置。 |
| 预览共享真实窗口的句柄或快照 | 快照一跑就过期；共享句柄等于让非界面线程读界面状态，且两份消费者会互相覆盖。 |

**何时重新评估「通用多窗口表」**：出现第三个独立的事实窗口消费者（例如并排比较视图、跨会话结果窗、缩略图）；预览需要可交互（选区、查找、超链接），此时归约与查找必须认识第二份窗口；需要把范围窗口跨进程暴露给脚本或桥接；或实测表明两份屏幕值传递造成可测量的帧率下降。在这些条件出现之前，不要为了对称把两个槽合并成映射表。
