# ADR-0020 · 可执行目标收敛为一个，CLI 改为协议薄客户端

- 状态：已采纳（取代 ADR-0016 中「两个可执行目标」的条款；其余条款继续有效）；部分被 [ADR-0030](0030-foreground-control-plane.md) 取代（§2/§5）。

## 背景

ADR-0016 把仓库拆成应用层 crate 加两个可执行目标：`apps/desktop`（有窗口）与 `apps/cli`（命令出口）。第二个目标落地后暴露出两个问题。

1. **它没有自己的实现。** 盘点全部子命令，只有环境体检是独有逻辑；其余——单条命令执行、会话增删与导入、远端 exec、SFTP 列目录与传输、布局读写、能力面清单——都是库调用的薄壳。也就是说它是「第二个前端」，不是「第二个实现」，正是会话所有权模型要收敛掉的形态。
2. **两个进程各持一部分能力，边界开始含糊。** 远端会话该由谁持有、脚本该连谁、能力面清单以哪份为准，都变成了要解释的事。

同时方向已经澄清：CLI 的后续目标是**桥接协议的薄封装**——只讲协议，不链接本仓库的 crate，不自持会话。会话的所有者是 desk，其他一切入口都是客户端。

## 决策

### 1) 删除 `apps/cli`，`apps/` 只留 `desk`

- 工作区成员里去掉该成员，目录整体删除，构建与校验脚本中针对它的检查项（第二个二进制的端到端、它的依赖表检查、它的 `.await` 扫描范围）一并删除。
- 事实基线随之变化：`apps` 由二变一，用例总数与检查项数按实际减少登记。这类数字必须跟着代码走，否则文档会在第一次核对时被判为失真。

### 2) CLI 的未来形态：桥接协议的薄客户端

未来若确有脚本或持续集成入口的需求，新 CLI 必须同时满足三条：

1. **只讲协议**：走桥接层的 JSON-RPC 2.0，方法清单来自 `describe`，客户端可由 `stub` 生成器自动产出。
2. **不链接 crates**：依赖表里不得出现任何 `term-*`；`serde_json` 之类的纯数据依赖可以。
3. **不自持会话**：所有会话操作落在 desk 持有的会话上。

位置不进 `apps/`：`apps/` 的定义恢复为「本仓库的可执行目标」，且只有一个。薄客户端放 `tools/cli`（独立工作区或独立仓库），由使用方按需构建。

### 3) 能力空洞记账

删除一个二进制不等于能力消失，也不等于能力还在。逐条记账，并区分「删除造成的空洞」与「新增能力的缺口」：

| 曾由 CLI 提供 | 现在谁能做 | 处置 |
|---|---|---|
| 环境体检 | `desk doctor` | 并入 desk 的无窗口子命令：判定与采集拆成两份，判定是纯函数、可单测，规则原样搬过来 |
| 能力面清单 | `desk capability [--json] [--all]` | 并入；JSON 字段名与文档口径**逐字同名**，不再出现「注释承诺一套、实际输出另一套」 |
| 单条命令执行 | `desk --headless --exec` | 覆盖，形态不同：打印最终网格文本，不打印原始字节。退出码一并补齐——无窗口执行的返回值带一个可空的退出码，`None` 表示「没有退出码」这种诚实状态，不伪造成 1，desk 侧冲刷输出后透传 |
| 会话增删、会话导入 | 界面可做，库在 | 等桥接方法，不补独立直连 |
| 远端 exec | 界面可做，连接层在 | **不补直连**：禁止第二个自持远端会话的进程 |
| SFTP 列目录与传输 | 界面浏览可用，传输未接 | 等 `desk serve` 暴露 SFTP 方法 |
| 布局读写 | 库在 | 等桥接方法，或在 desk 补一条无窗口子命令 |
| 桥接服务 | `desk serve` | 并入（见 ADR-0022）：只绑回环、token 文件、首条请求必须握手、锁屏拒服 |

顺序判断：先行落地的是同步类入口（环境体检、能力面清单、单条执行、桥接服务）；剩下的是「桥接先有方法、CLI 形态才有意义」的那批，它们需要一个真正的协议客户端来做，不必挤进 desk。

### 4) 判据

| # | 判据 | 检查方式 |
|---|---|---|
| C1 | `apps/` 下只有一个成员 | 列目录，结果只能是 `desk` |
| C2 | 仓库里没有旧二进制名的残留引用 | 全局检索，只允许出现在历史决策记录里 |
| C3 | 未来若出现新 bin，零 `term-*` 依赖 | 依赖表检查 |
| C4 | 文档中的计数与实测一致 | 文档核对脚本 |

## 后果

- **正面**：依赖图少一个叶子；构建少编译一个二进制；不再有两套「同一能力」的实现漂移；`apps/` 的语义变干净，`apps/` 等于「可以双击或直接执行的东西」。
- **负面**：删除瞬间确实留下入口空洞——环境体检与能力面清单一度无处可去，随即在同一分支并入 desk 的无窗口子命令。剩下的缺口是新增能力，不是删除造成的。
- **不改的**：`term-runtime` 里的持久化、布局状态、会话导入这些库实现一行不动；删掉的只是调用它们的那个壳。库能做的事没有减少，只是不再有第二个调用方。
- **复查触发**：持续集成或自动化确实需要命令行入口（不是「觉得应该有」）→ 先做桥接服务，再生成薄客户端，不得把逻辑写回客户端；desk 的无窗口子命令超过五条，或 `main.rs` 的参数解析开始影响可读性 → 把子命令拆成 `cli/` 下的模块，仍在同一个二进制内，**不**恢复第二个可执行目标；需要跨机器远程控制 → 那是桥接服务的 TCP 加 token 形态，不是 CLI 的职责。

## 备选方案与否决理由

| 方案 | 否决理由 |
|---|---|
| 保留 `apps/cli` 作为「顺手能用」的入口 | 两套同一能力的实现会在第一次改行为时分叉；且与会话所有权模型冲突——它要自持会话才有意义 |
| 把 CLI 的逻辑并进 desk 主二进制的参数解析 | 这正是本 ADR 采取的方向，但只并入「无窗口且不自持会话」的部分；把会话管理搬进来等于让 desk 在窗口态与命令态各有一套会话生命周期 |
| 新 CLI 继续链接本仓库的 crates | 等于给语义层造第二个宿主；协议才是稳定接缝，库的内部结构不是 |
| 把薄客户端放进 `apps/` | `apps/` 的定义是本仓库的可执行目标；客户端由使用方按需构建，放进来只会重新长出第二个叶子 |
| 删掉就当能力消失，不做记账 | 使用者会直接撞上空缺，且无法区分「等桥接方法」与「明确禁止直连」两种性质完全不同的缺口 |
| 为补齐空洞，让 desk 承接所有 CLI 子命令 | 会话增删、导入在无人值守的命令行里没有交互上下文；这些能力属于界面或协议客户端，不属于无窗口入口 |
