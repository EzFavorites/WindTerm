# ADR-0023 · 脚本 API 与远程 API 共用一张能力面：一张表、一个语义核

- 状态：已采纳（补强 ADR-0019 的单一能力面要求，不改变其既有决策）；部分被 [ADR-0030](0030-foreground-control-plane.md) 取代（「两个前端 / Exposure 三档」表述）。

## 背景

ADR-0019 要求任何客户端都只能经同一组动词触达会话。实现过程中曾出现两张清单：远程方法表由 `term-core::surface` 声明，脚本原语在脚本引擎里单独注册。重叠的动词被注册两遍，各自独有的动词在另一个前端完全不可用。

问题不止是「少一个功能」。任何一侧新增动词，另一侧不会跟随，也没有机制会报警；于是同一个意图在两侧行为不同：

- 脚本侧读输出有游标，读到哪里由上次取走点决定，超时为显式失败；
- 远程侧只有一次性等待与屏幕快照，快照不消费输出，洪水输出下必然漏读。

这种差异不会立刻报错，只会在若干步之后表现为「卡住了」或「结果少了一段」。ADR-0019 明确禁止静默空成功与漏匹配，因此名字一致不足以满足要求，还需要语义一致。

另一条约束决定了实现位置：桥接的运行时依赖被白名单限定为描述层与序列化，且必须零异步。它不能依赖脚本引擎，所以「共用」只能落在两层——**共用一张表**，以及**共用一个语义核**。

## 决策

### 1. 一张表：`term-core::surface::METHODS`

每个条目是 `MethodSpec`：线上名、一句话说明、参数的 JSON Schema、结果的 JSON Schema、方法类别、对哪个前端可见。表是唯一真相，远程自描述、桩生成、脚本注册、文档清单全部从它派生。

### 2. `Exposure` 只有三档

- `Rpc`：只对远程可见（当前只有自描述动词）。
- `Script`：只对脚本可见，因为远程有更省往返的等价表达。
- `Both`：绝大多数会话动词。

分档只标注「这个动词该出现在哪个前端的动词表里」，不是两套 API 的开关，不产生第二套语义。

### 3. 一个语义核：`term-script::ScriptSession`

捕获游标、行级过滤、超时显式失败、协作式取消只有一份实现。

- 脚本前端把 `ScriptSession` 的方法包成 Rhai 全局函数，只做类型适配。
- 远程前端 `DeskSurface` 按会话持有同一个 `ScriptSession` 实例，因此 `read`、`read_until`、`wait_any` 在远程与本地共享同一套游标语义。

远程侧必须持有游标，因为 `read_until` 的承诺是「自上次取走点往后读到哨兵」。无状态实现只能每次从屏幕重读，那就是漏读。桥接是一条串行管道，按会话持游标不引入并发问题。

`ScriptSession` 只认 `Session` trait，表中也不出现 ssh、sftp、telnet 等字样，协议无关原则不受影响。

### 4. 漂移防线是集合相等断言，不是代码生成

两条断言各钉一侧：

- 脚本引擎已注册的函数名集合，必须等于表中脚本可见的动词集合；
- 远程分发分支集合，必须等于表中远程可见的动词集合。

任一侧增删动词而未同步另一侧，测试即失败。不采用宏或运行时反射生成注册：参数类型适配本就需要手写，Rhai 的整数与浮点双重载也无法自动生成；而「表写得漂亮但没人对账」正是漂移的成因，断言比生成更直接。

### 5. `MethodKind` 增加 `Stream`

客户端需要区分两类取数：

- `wait` 是一次性同步：登记、命中、结束，重复调用安全（每次重新登记）。
- `read`、`read_until`、`wait_any`、`wait_idle` 推进游标：重复调用会**吃掉**上次未读完的数据，这是语义而非缺陷。

因此流式动词必须有独立类别，`describe` 如实告知「该动词消费输出，不要并发或重试式调用」。

### 6. 形状与命名收敛

- **会话描述符只有一种形状**：`session_list` 的每一项、`session_open` 与 `session_use` 的结果共用一份 schema（名字、存活、退出状态），客户端可以把开出来的会话直接塞回清单，不需要记两套键名。
- **写字节与按键分开**：`write` 送原始字节，内容不被解释；`keys` 送键名，按会话当前光标模式翻译成字节序列。合并成一个「聪明」的动词就必须在运行期猜这串字符是文本还是键名，猜错是**静默发错字节**，程序收到不认识的序列后不动，作者只看到卡住。分开之后，认不出的键名是参数错误，并能点名是哪个键。
- **键表只有一份**：键名到字节的映射在 `term-core::keys`，界面按键与脚本 `keys` 用同一张表；整批键名翻译成功后才写出，避免发出半截按键序列。
- **`screen` 返回整屏**：整屏文本、行列与光标一并返回，不为光标单开一个动词。
- **`facets` 返回会话能力**：回答「这条会话能做什么」，而不是「本端支持哪些动词」；后者是自描述动词的职责。
- **错误形状统一**：跨能力面、脚本与桥接使用同一 JSON 错误结构，避免不同客户端看到不同形状。

### 7. 登记时点必须对齐两侧

`ScriptSession` 在**构造时**登记捕获器。脚本侧的构造发生在脚本开跑之前，写到一半的输出一定在窗口里。

远程侧如果懒创建游标（首次读取才建），客户端最常见的写法 `session_open → write → wait → read` 就会丢掉 `read` 之前的输出——同一条脚本搬到远程就少一段。因此 `session_open` 成功后立刻为该会话建立游标。

边界写清楚：界面里用户自己开的会话不在此列。客户端是后来才接上的，从接上那一刻开始读本来就是它的语义。

### 8. 退出状态必须是真实原因

会话线程退出后，命令队列的接收端随之关闭，若查询只看到「已结束、无状态」，退出码就丢了——而客户端分辨「正常结束」与「崩溃」靠的正是这一个字段。

退出原因由会话线程在同一条线程里写入与句柄共享的格子，查询先读它；格子只在退出那一刻写一次，不是缓存读。状态文本由会话 IO 层定义，能力面原样透出，不另编一套。

### 9. 兼容层只提供对象形状

第三方脚本 API 习惯以对象组织调用（会话对象、屏幕对象等）。兼容门面把这种**对象形状**映射到本仓动词，单独注册、不进能力面表，也不参与集合相等断言。

架构结论只有三条：它不解释脚本语言；它不为缺失成员制造空成功；对象名不得出现在 `describe` 的 schema 里。能力面描述的是「会话能做什么」，把对象名写进表会让远程自描述长出与本端无关的词汇。

## 后果

- **换客户端不换行为**从口号变成结构保证：脚本、远程与后续 Agent 看到同一组动词与同一套语义。
- **新增动词流程固定**：表中加一条、两侧各自实现或暴露、两条断言变绿。可见性分档本身就回答了「该出现在哪一侧」。
- **流式语义对远程可用**：批量巡检可以「读到哨兵再往下」，不必靠屏幕快照猜。
- **`DeskSurface` 由无状态变为持有按会话的游标**：会话关闭时必须清理，否则游标泄漏。
- **`ScriptSession` 成为跨前端公共语义核**：它的一举一动同时影响脚本与远程，改动必须同时跑两侧测试。
- **能力面表变长**，自描述输出变大。这是功能代价，不是设计缺陷。
- **兼容层是有边界的**：它只改调用形状，不扩大能力面；缺什么就报什么，不假装成功。

## 备选方案与否决理由

- **两张清单各自维护**：漂移没有任何报警机制，且已经产生语义分叉。否决。
- **桥接直接调用脚本引擎**：桥接运行时依赖白名单与零异步约束不允许。否决。
- **用宏或反射生成两侧注册**：类型适配仍需手写，Rhai 双重载无法自动生成；生成还会掩盖「该不该出现在这一侧」的判断。否决，改为集合断言。
- **保留 `send` 并内部判断文本或键名**：猜错即静默发错字节，是自动化里最贵的一类错误。否决，拆为 `write` 与 `keys`。
- **为 `cursor_pos`、`terminal_size` 单开远程动词**：`screen` 已返回行列与光标，单列只是多一次往返。否决，标为仅脚本可见。
- **把兼容层对象写进能力面表**：会让远程自描述出现对象名，违反协议无关与「schema 不出现对象名」的约束。否决，单独注册。
- **流式动词沿用普通读类别**：客户端会把「重复读取会丢数据」当成可重试的幂等读。否决，新增 `Stream` 类别并在描述中写明。
