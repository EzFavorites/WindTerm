# ADR-0005 · 自有代码采用 Apache-2.0

- 状态：已采纳

## 背景

许可证决定三件事：谁能用、谁能改、改了要不要回流。对一个以「能自由加功能」为立项理由的项目，这三件事直接关系到动机是否被自我否定。

## 决策

自有代码采用 Apache-2.0；插件 SDK 与示例插件同许可证，不做例外。

### 理由

- **动机一致性**：立项的理由是「既有终端要么闭源、要么扩展受限，想要的功能加不了」。若本项目改用 GPL 系列，等于把同一个问题复制给下游——企业不能改、不能嵌、不能分发定制版。只有宽松许可才能让「任何人都能加功能」这个承诺成立。
- **专利授权**：Apache-2.0 含明确的贡献者专利许可。终端产品涉及加密、压缩与协议实现，专利风险不为零；MIT 没有这一条。
- **生态一致**：SSH、GUI、插件运行时这几层的关键依赖都是 Apache-2.0 或同族许可，统一许可降低依赖白名单的维护成本。
- **企业可采用**：这是扩大用户面的必要条件。copyleft 许可会让法务流程直接卡住内部试点。

## 后果

正面：

- 任何人可闭源分发、可嵌入商业产品、可做企业内部定制。
- 贡献者的专利风险被覆盖。
- 与依赖生态一致，合规审计简单。

负面：

- 没有 copyleft 保护：他人可以 fork 后闭源，不回馈社区。
- 可能出现改名换皮的商业版本，甚至被误认为官方版本。

接受的取舍：本项目追求「被广泛使用」，不追求「强制回流」。若将来出现明显的闭源滥用，可考虑对插件 ABI 规范文档改用 CC-BY-4.0 强制署名，但不改变代码许可。

### 配套要求

1. **第三方依赖清单要维护**：列出全部依赖及其许可证，其中 MPL-2.0 的 `serialport` 需要单独标注。
2. **许可证门禁**：发布前跑许可检查，出现 GPL、AGPL、SSPL 直接失败。允许列表为 MIT、Apache-2.0、BSD-2/3-Clause、ISC、MPL-2.0、Unicode-3.0、Zlib。
3. **贡献流程**：不要求 CLA，采用轻量的来源声明（`Signed-off-by`），符合开源项目的轻量治理。
4. **商标**：Apache-2.0 不授予商标权。README 必须声明名称与标识不随代码许可授权，避免出现官方背书的假象。

## 备选方案与否决理由

| 方案 | 否决理由 |
|---|---|
| MIT | 无专利条款，对含加密实现的软件风险敞口偏大 |
| GPL-3.0 | 与「让所有人能加功能」的立项动机冲突，企业采用受阻 |
| MPL-2.0 | 文件级 copyleft 是合理折中，但生态认知度低、法务沟通成本高 |
| AGPL-3.0 | 本项目无网络服务形态，AGPL 没有实际收益，只会缩小用户面 |
| 双许可（Apache-2.0 + 商业） | 单人项目没有精力运营商业授权，且与「完全开放」的定位冲突 |
