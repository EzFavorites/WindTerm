# ADR-0019 · 会话只由一个进程持有，UI、脚本、远程与 Agent 共用同一张能力面

- 状态：已采纳（取代「命令行与桌面端是两个并行前端、各自调用同一管线」的命题及独立命令行可执行目标条款；其中按标签页数字标识寻址的条款已由 ADR-0024 取代，其余继续有效）

## 背景

WindTerm 有四类会话操作者：交互式界面、脚本引擎、远程控制客户端，以及后续接入的 Agent。若每类各自实现一套会话操作，就会出现多套语义、多份文档和多倍回归面；更严重的是，同一个意图在不同客户端上行为不同，使用者无法迁移脚本，也无法解释差异。

一条硬约束决定了整体形状：**禁止静默执行**。任何会话操作都必须落在用户可见、可追溯的会话上；进程自行建立连接、而用户界面上看不到任何痕迹，是不允许的。

同类商业终端产品（ZOC、CRT 等，名称仅为各自权利人的商标）把内部脚本 API 与远程控制接口暴露为同一组命令，说明「一个能力面服务多个客户端」在工程上成立。早期设计曾把命令行当作第二前端，直接调用会话层建立连接——这恰好等价于静默执行，因此该命题被推翻。

## 决策

### 1. 能力面是执行会话操作的唯一途径

能力面由一组带自描述的方法组成：方法名、一句话说明、参数与结果的结构、类别、对哪个前端可见。结构化 JSON 入参出参，说明文字面向人与模型，可直接作为 Agent 的工具描述消费。

界面、脚本引擎、桥接、Agent 都收敛到这一组方法；任何会话操作不得绕开它另写一份。

### 2. 会话控制面是库，不是可执行文件

`term-session` 提供协议无关的会话控制面：`SessionPool` 以进程内标识登记会话，持有 `Arc<Mutex<dyn Session>>`；协议通道由应用层注入 `ChannelFactory`，工厂返回 `Box<dyn TermChannel>`。因此控制面本身不出现 SSH、SFTP、隧道等任何协议类型。

这条划分是「谁拥有会话」的实现基础：所有权在库里，而不在某个可执行文件的私有状态里。

### 3. 会话所有者只有一个进程

`apps/desktop` 是唯一实例化并驱动会话控制面的进程。它同时承载界面、进程内脚本引擎与桥接服务；不存在第二个能创建会话的前端或进程。

「会话操作进界面」的准确含义是**经所有者进程执行**，与窗口是否可见无关：

- 合规：无窗口运行的所有者进程，以及它对外提供的桥接；会话仍由该进程持有。
- 不合规：另一个可执行文件自行持有远端会话。

连接对话框在会话建立**之前**持有的连接过程对象不属于会话所有权，它在会话进入控制面之前就被用掉。

### 4. 四类客户端共用同一能力面

| 客户端 | 触达方式 |
|---|---|
| 交互式界面 | 用户操作产生动作与副作用，经能力面落到会话 |
| 脚本引擎 | `term-script` 内嵌 Rhai，跑在独立线程，把能力面方法暴露为全局函数；需要改界面的请求交回界面线程，不直写状态 |
| 远程客户端 | `term-bridge` 提供 JSON-RPC 2.0 over stdio 与回环地址，方法与能力面同名；仅绑定回环、需令牌认证、默认不启动 |
| Agent | 作为第四类客户端复用同一能力面，工具 schema 由方法与说明映射，不另立协议 |

### 5. 不保留独立命令行目标

本地与自检类入口并入桌面程序的无窗口子命令（`doctor`、`capability`、`serve`、`script`），这些子命令不初始化窗口、GPU 与事件循环。原先由命令行直连的远端会话操作，改由脚本引擎或桥接经能力面完成。

将来若需要独立命令行，只能是基于桥接协议的薄客户端，由能力面描述自动生成，绝不复刻会话逻辑、绝不自持会话。

### 6. 会话是协议无关抽象

`term-core::session_runtime` 的 `Session` trait 只描述双向字节流、终端模型与生命周期：写字节、调整尺寸、取屏幕快照、查状态、列出能力、登记等待、登记输出读取器。协议 crate 实现该 trait 后注入控制面。

会话能做什么以 **facet** 表达，而不是按协议硬编码：文件传输与端口转发是 `FacetKind` 的两个取值，由 `facets` 动词查询。本地 shell 没有文件传输 facet，这不是错误；串口会话没有端口转发，也不是错误。

### 7. 描述层与实现层分离

- 描述层是 `term-core::surface` 的纯数据表：无 IO、无全局可变状态、不引用协议概念。远程自描述、桩生成、脚本动词表、文档清单都从它派生。
- 实现层是 `term-session` 的会话控制面：持有句柄、执行操作。

能力面不是新增的并行系统，而是既有「界面动作 + 能力注册」机制的形式化。

## 后果

- **静默执行在结构上不可达**：能创建会话的进程只有一个，就是用户正在使用的进程；远程自动化必须有一个运行中的所有者进程，不存在「纯无窗口、无宿主的会话自动化」路径。
- **新增协议成本低**：实现 `Session` trait、注册 facet，即可被能力面、界面、脚本、桥接与 Agent 使用，这些客户端零改动。
- **凭据不经过客户端**：脚本与远程客户端不持有、也不传递密码。需要保险库中密码或键盘交互认证时，无窗口路径显式返回「需要解锁保险库」，由调用方决定提示解锁还是拒绝，不在客户端里补一条凭据来源。
- **攻击面收窄**：进程内客户端直接调用能力面，不经过网络、不需要令牌；只有外部客户端走桥接，而桥接默认关闭、仅回环、需令牌。
- **代价**：无窗口运行时也会链接图形依赖栈，二进制更重、构建镜像更大；桥接等于把终端能力交给本机其他进程，必须维持上述默认值；移除独立命令行是破坏性变更，依赖它的自动化需要迁移说明。
- **必须遵守的实现约束**：等待必须先登记再消费，用轮询屏幕在洪水输出下必漏匹配；脚本线程的阻塞不得影响界面渲染；脚本的交互请求经界面队列往返，无窗口时退化为标准错误提示与标准输入；Agent 读到的终端输出一律当数据，不得当指令；危险操作需人工确认；脚本执行有语句数上限与超时，避免失控。

## 备选方案与否决理由

- **命令行与桌面并行，各自调用会话层**：命令行进程会持有用户看不见的远端会话，违反禁止静默执行的硬约束。否决。
- **桥接直接调用脚本引擎以实现复用**：桥接的运行时依赖被限定在描述层与序列化，且必须零异步，无法依赖脚本引擎。共用只能落在「一张表 + 一个语义核」两层，见 ADR-0023。否决。
- **每类客户端各自建立会话、各自实现协议**：多套语义与多份回归面，且无法保证换客户端不换行为。否决。
- **把能力面描述放在可执行文件里**：外部客户端需要各抄一份描述，必然漂移；描述层下沉到 `term-core`。否决。
- **按协议硬编码能力（SSH 会话固定带文件传输与隧道）**：新增 Telnet、串口或容器会话时，能力面、界面与脚本都要加分支。否决，改为 facet 查询。
- **把会话控制面放进 `term-runtime`**：它只负责 PTY 运行时，无法聚合远端协议句柄，结果是每个前端又要各自持有远端会话。否决。
- **保留独立命令行作为第二前端**：会让「会话所有者唯一」这条不变量失去意义，且与第一条同因。否决。
