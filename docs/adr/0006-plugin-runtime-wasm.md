# ADR-0006 · 插件运行时选用 WASM（wasmtime）

- 状态：已采纳

## 背景

「能加功能」是本项目的立项理由，插件系统因此不是锦上添花，而是产品承诺本身。它必须同时满足：可扩展、不拖垮宿主、不成为安全后门、支持多种语言编写、具备可分发的信任链。

候选：

- A. WASM（`wasmtime`，Apache-2.0 WITH LLVM-exception）
- B. JS 插件，在 WebView 里执行
- C. 原生动态库（`.dylib` / `.dll` / `.so`）
- D. 子进程 + JSON-RPC

## 决策

采用 WASM 加 `wasmtime`，配合能力清单（capability manifest）与签名校验。

### 理由

- **隔离性**：WASM 沙箱内越界即 trap，插件无法读写宿主内存，也无法直接触碰文件系统与网络。JS 插件跑在同一个 WebView 上下文里，等于把主界面的安全性交给插件作者，这一点不能接受。
- **性能可预测**：日志高亮、命令块识别这类解析插件要处理 MB 级字节流。WASM 没有 GC 抖动，行为比 JS 更可预测。
- **语言中立**：Rust、Go、AssemblyScript、Zig 都能编译到 WASM。终端用户里 Rust 与 Go 开发者占比不低，限定 TypeScript 会砍掉相当一部分潜在作者。
- **宿主同栈**：`wasmtime` 是 Rust 原生项目，不需要 FFI 胶水；而原生动态库方案会让插件获得与宿主同等的权限。
- **崩溃隔离**：插件 panic 或死循环被 trap 捕获，宿主继续运行。原生动态库方案里一次段错误就是整个应用退出。

### 关键设计约束

1. **默认零能力**：宿主侧只暴露日志，其余能力必须显式声明。
2. **能力不可自授权**：插件不能申请「以后再说」的权限，任何能力变更都要用户重新确认。
3. **v1 禁止的能力**：文件系统直读、任意网络访问、启动进程、读取凭据。需要这些能力的功能走原生扩展通道，并要求用户显式授予。
4. **签名不可绕过**：除用户显式开启开发者模式（需醒目警告）外，未签名插件不得加载。
5. **fuel 与内存双限**：单次调用有 fuel 上限，实例有内存上限，超出即终止并记录。

## 后果

正面：

- 安全边界清晰：默认零能力，按清单授权。
- 一个 `.wasm` 通吃三平台，分发与平台无关。
- 可做资源限额（内存上限、fuel、超时），插件拖不死 UI。

负面：

| 负面 | 处理 |
|---|---|
| 宿主需维护 ABI 与胶水层，是一次性成本 | 接受；v1 ABI 保持长期不破坏，避免插件作者反复重编 |
| 插件调试体验不如脚本 | 提供本地加载与日志透传的开发子命令 |
| 复杂 UI 插件受限，不能直接绘制界面 | v1 只开放「命令 + 输出处理」，自定义面板留到 v2 |
| 简单插件也要工具链，比写脚本重 | 提供 AssemblyScript 模板，把门槛降到「会写 TS 就能写插件」 |

边界说明：用户自己写的自动化走内嵌脚本引擎与能力面（见 `docs/scripting.md`），与本 ADR 是两条路径——脚本是用户在自己机器上写的可信代码，WASM 沙箱面向分发给他人使用的第三方插件。

## 备选方案与否决理由

| 方案 | 否决理由 |
|---|---|
| JS 插件（WebView 内） | 无隔离，插件可读 DOM、可读凭据、可发网络请求，与「默认无遥测」的承诺直接矛盾 |
| 原生动态库 | 无沙箱、崩溃即全局退出、三平台各编译一次、签名链复杂 |
| 子进程 + JSON-RPC | 隔离尚可，但 IPC 开销在字节流处理场景不可接受，进程管理复杂度也高 |
