# ADR-0003 · VT 引擎边界：先把解析放在前端 xterm.js

- 状态：已被取代（被 ADR-0008 取代）

后续演进：UI 改用 egui 后进程内不再有 xterm.js，「VT 在前端」的前提消失，改为后端解析 + 自研网格渲染（ADR-0008）。本文保留下来的价值，是当时对两种位置的取舍与迁移预案。

## 背景

终端产品的技术核心是 VT 状态机：解析 ANSI 转义序列并维护屏幕缓冲。它同时决定三件事——兼容性（vim、htop、tmux 能否正确渲染）、上层能力的可能性（搜索、命令块、折叠、审计、跨会话索引）与性能上限（大吞吐下的帧时间与内存）。

可选位置只有两个：

| 位置 | 引擎 | 后果 |
|---|---|---|
| 前端 | xterm.js | 后端只搬字节；语义能力受限于前端接口；VT 状态随窗口销毁而丢失 |
| 后端 | 进程内 VT 库 | 语义能力全部可在后端实现；但前端必须自研网格渲染器 |

## 决策

采用前端方案：VT 解析与渲染都在 xterm.js，Rust 侧只负责字节流、背压、协议与日志落盘。

同时落实三条纪律，使迁移到后端成为计划而不是愿望：

1. 前端只通过自有 `TermView` 接口操作终端（`write` / `resize` / `focus` / `getSelection` / `scrollTo`），禁止散调 xterm.js API；
2. 语义功能（搜索、命令块识别、时间戳）抽象为 `SemanticIndex` 接口，先由前端实现，迁移后换后端实现；
3. 后端不得持有任何像素或单元格概念，会话 ID 与终端实例 ID 分离。

### 理由

选择前端方案的原因只有一个：单人开发的约束压倒一切。后端方案的成本集中在六块自研工作上，每一块都是独立工程：

| 项 | 为什么必须自研 |
|---|---|
| 字体整形与连字 | 需要 harfbuzz 级排版能力 |
| emoji 与 CJK 双宽判定 | 东亚宽度表、ZWJ 序列、区域标志 |
| 输入法候选框定位 | 要把光标屏幕坐标回传给系统 |
| 选区 | 线性、矩形、双宽边界，三套坐标系互转 |
| 滚动惯性 | 网格渲染天然整行跳变 |
| 无障碍 | 影子 DOM 或平台无障碍桥 |

xterm.js 在这些方面已经具备可用实现。把上述工作全部做一遍，在 v1 的预算里不可接受。

仍然要预留后端方案，是因为前端方案有一个不可协商的天花板：

- 搜索只能覆盖前端缓冲区，容量受限；
- 命令块、折叠、跨会话索引都需要「看到全部输出」，而前端方案的后端只有裸字节；
- 大回看的内存曲线由 JS 堆决定，做不了压缩。

当这些成为主要问题，后端方案是唯一出路。

## 后果

正面：

- 交付速度快于后端方案，输入法、选区、字体与无障碍直接继承浏览器能力。
- 前后端边界清晰，两侧可以分开推进。

负面：

- 「无限回看」无法真正实现，只能做「热区缓冲 + 冷区日志检索」。这是产品承诺上的实质退让，必须在文档里讲清楚，不能含糊。
- 命令块折叠这类语义功能要基于前端缓冲区接口反推，成本高于后端方案。
- VT 状态在渲染进程里，窗口重开即丢；布局恢复只能恢复结构，不能恢复内容。

### 迁移预案

触发条件（任一满足即启动）：

1. 输入法问题在前端方案下无法解决；
2. 用户反馈的主要问题集中在大回看、搜不到历史、输出卡顿；
3. 命令块折叠或跨会话搜索在前端架构下的实测成本高于重写。

目标形态：后端解析 + 自研网格渲染，UI 层不动。届时本 ADR 由新决策取代。

## 备选方案与否决理由

| 方案 | 否决理由 |
|---|---|
| 直接上进程内 VT 库 + egui | 放弃 Web UI 的全部积累，且输入法与排版仍要自研 |
| 用 wezterm 的终端库 | 同上，且该库未在 crates.io 常规发布，供应链风险更高 |
| 同时维护前端与后端两套渲染 | 单人不可能，直接排除 |
