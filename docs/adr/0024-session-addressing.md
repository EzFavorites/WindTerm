# ADR-0024 · 能力面按会话名寻址，数字标识不进入线上形状

- 状态：已采纳（取代 ADR-0019 中按标签页数字标识寻址的条款；沿用 ADR-0023「一张表两个前端」的结论）

## 背景

早期能力面用 `"tab": <整数>` 寻址。三个问题随实现暴露出来：

1. **名不符实**。参数里装的其实是会话标识，与会话一一对应，并不存在第二套标识体系；而名字说的是标签页——标签页是纯界面概念。桥接侧只开一条会话，根本没有标签页，远程客户端看到的动词表里却写满了 `tab`。
2. **把能力说小了**。界面内的脚本面板一度拒绝「打开会话」，因为动词名把「开会话」与「开标签页」钉成了同一件事。它本来有能力开会话，加不加标签页该由界面决定。
3. **数字标识不可移植**。会话标识是进程内自增，重启即变。于是「把脚本存下来明天再跑」不成立——而这正是脚本 API 的主要用途。

同类商业终端产品（CRT 等，名称仅为各自权利人的商标）以会话对象、按会话名连接的方式暴露脚本能力，寻址键是名字而不是数字，验证了这条方向。

## 决策

**能力面一律按会话名（字符串）寻址；数字标识不出现在任何线上形状里。**

### 1. 参数与方法名

- 参数 `"tab": 7` 改为 `"session": "prod-db"`。
- `tab_open`、`tab_close`、`tab_list`、`tab_use`、`tab_current` 相应改为 `session_open`、`session_close`、`session_list`、`session_use`、`session_current`。
- 会话描述符改为「名字、存活、退出状态」，不含数字标识；列表结果由 `{"tabs": [...]}` 改为 `{"sessions": [...]}`。

方法名的改名不改变 ADR-0023 的结论：一个动词、两个前端、一种形状，与键叫什么无关。

### 2. 寻址名在开会话时定下，且池内唯一

- 名基：来自会话库的会话配置名；命令会话用命令文本；本地 shell 用配置名。
- 冲突时按 `base`、`base-2`、`base-3`… 递增，与「同名文件不覆盖」同一思路：不静默顶掉别人的名字，也不报错让调用方自己想新名字（脚本里连续两次 `session_open("cat")` 是很自然的事）。
- 唯一化发生在会话池插入时；遍历现有名字找第一个空位，因此用户手工起的 `cat-2` 也算占用，再来一条 `cat` 会得到 `cat-3`。
- **唯一化之后的真名必须回报给调用方**：返回值是池中登记的名字，不是调用方传入的名基。否则客户端拿名基去寻址会打中另一条会话。

### 3. 改名只改显示名，不改寻址名

界面里的重命名改的是标签页显示名，不动池中的名字。这不是疏漏，而是判据：**寻址名是身份，显示名是标签**。池名在插入后即冻结。

代价是用户改完名，脚本仍用旧名——这是正确的，脚本引用的是「那条会话」，不是「那个标签」。需要改名后继续引用时，用 `session_list` 重新取。

### 4. 没有数字标识的逃生门

不提供 `"session": 7` 这样的双类型参数。理由与 `write` 和 `keys` 拆分的判据同源：**一个参数两种解释**，猜错不会报错，只会表现为「打中了另一条会话」，比直接失败昂贵得多。同名歧义已由插入时唯一化消除，不需要第二条路径。

### 5. 错误

- 未知名字：`not_found`，文案点名那个名字，并提示用 `session_list` 查看当前会话。
- 不报「歧义」：名字在插入时已唯一，运行期不存在歧义状态。

### 6. 参数形状先于会话存在性

每个动词先校验自己的其它参数（文本、模式、分隔符、安静窗口等），最后才解析会话名。

理由是一个明显写坏的请求（缺文本、模式列表里有非字符串）若被报成「找不到会话」，客户端会去查会话列表——查了也没用，真正要改的是参数。

唯一需要提前校验的例外是按键名：键名翻译依赖会话当前的光标模式，所以先按非应用模式翻一遍**只为校验**键名是否存在，解析完名字后再按真实模式翻第二遍。方向键在两种模式下都在键名表里，这一遍不会误判。

### 7. 线上只有名字，内部身份另行分层

数字标识在实现内部仍然存在：它是进程内自增的运行实例标识，用作会话池索引，重启归零。

这条内部标识**不进入动词描述符**，也不作为参数备选。逻辑会话与运行实例是否要分成两层、如何持久化，是独立问题；本 ADR 只约束线上形状：能力面看到的一律是名字。

## 后果

- **脚本可移植**：名字跨进程稳定，存下来的脚本明天还能跑。
- **动词表与前端一致**：桥接侧不再出现自己不具备的概念。
- **界面侧「不能开」的限制失去理由**：闸门不再叫「界面里不能开标签页」，只剩下「这条界面还没把池子画出来」。后者属于另一项决策，不是寻址问题。
- **名字成为全局命名空间**：唯一化规则必须在开会话、导入、恢复布局等所有入口一致，否则同一个名基会出现两种后缀规则。
- **名字变了旧脚本会打空**：唯一化或用户改会话库条目都会改变名字，旧脚本收到 `not_found`，而不是静默打错。这是选择「唯一」换来的确定性。
- **实现代价**：会话池多一次按名查找；所有动词的 schema 需要一次性改写，描述符去掉数字标识。

## 备选方案与否决理由

- **保留数字标识寻址**：不可移植、名不符实，且让远程客户端看到自己不具备的概念。否决。
- **双类型参数（名字或数字都接受）**：一个参数两种解释，歧义只会在运行期表现为打错会话。否决。
- **插入时因重名报错，要求调用方改名**：脚本连续打开同类会话是常见写法，报错会把命名负担推给脚本作者。否决，改为递增后缀。
- **改名同时改寻址名**：正在运行的脚本引用的名字会中途失效，等于静默换目标。否决，改名只改显示。
- **对未知名字报「歧义」**：插入时已唯一化，运行期不会出现歧义；报歧义会让客户端以为应改用数字标识。否决。
- **把数字标识作为可选字段加进描述符**：客户端会开始用它寻址，等于把逃生门装回去。否决。
