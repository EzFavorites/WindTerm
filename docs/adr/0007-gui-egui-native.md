# ADR-0007 · 桌面 UI 改用 egui / eframe 原生渲染

- 状态：已采纳（取代 ADR-0002）

## 背景

ADR-0002 选择 Tauri 2 + WebView，理由是复用浏览器里的终端组件、交付最快。但该方案留了一个被记录为致命项的残留风险：WebView 的输入法行为不可控，且在本地难以复现和定位——出问题只能等平台修复，产品侧没有着力点。

当时的判断是：不赌 WebView 的输入法行为，改用纯 Rust 原生窗口，代价是自研终端控件。

## 决策

采用 `egui` / `eframe`（MIT OR Apache-2.0）作为唯一 UI 层，编译为单原生窗口，覆盖 macOS / Windows / Linux。窗口、标签页、分屏、侧边栏、设置弹窗全部由 egui 绘制，不嵌入任何浏览器运行时。

### 理由

- **消除不可控项**：原生窗口的输入法走系统输入法协议，问题可以在本地复现、定位、验证。把一个「要么通过、要么推倒重来」的外部依赖，换成「工作量确定、边界清楚」的工程量——这是风险偏好的正确调整。
- **许可与构建链**：MIT OR Apache-2.0，与自有代码一致；纯 Rust，没有 C++ 或 Qt 构建链，也就没有 Qt 的 LGPL 动态链接约束与静态链接的开源义务。
- **单二进制与小体积**：eframe 不用系统 WebView，也不打包 Chromium，产物是单个可执行文件。
- **与 VT 内核同进程**：终端状态是进程内的纯数据结构，解析侧与绘制侧共享快照，不需要跨进程序列化（见 ADR-0008）。

### 对既有判断的修正

早期否决原生框架的理由是「文本排版、输入法、选区、无障碍都要自研」。这个判断把两件事混在了一起：框架负责的部分与终端语义独有的部分。

重新划定范围后，egui 承担窗口、控件、布局、字体装载与输入事件分发；真正需要自研的只有终端语义层：

- 单元格网格与宽字符占位；
- 选区（线性、矩形、双宽边界）与三套坐标系的换算；
- 回看与重排；
- 鼠标上报与屏幕坐标的映射；
- 逐行字形缓存与脏区重绘。

范围这样切分之后，工作量降到可接受的程度，这是本决策能成立的前提。

## 后果

正面：

- WebView 跨平台差异归零：不再有三套内核的行为差异要维护。
- 渲染循环完全自控，适合做「大吞吐下一帧不丢」的优化。
- 启动与内存可控，符合轻量终端的定位。
- 与进程内 VT 内核天然衔接。

负面：

| 负面 | 严重度 | 处理 |
|---|---|---|
| 终端控件要自研 | 高 | 作为单一核心目标排期，不与之并行其他 UI 工作 |
| 表格、树、下拉、模态等控件要自绘或选型 | 中 | 按需自绘，或引入配套组件（如 `egui_extras`） |
| 无障碍能力弱于浏览器 | 中 | 明确列为已知限制，不承诺企业级无障碍 |
| 复杂文本整形与连字弱于浏览器 | 中 | 列为已知限制；终端场景以等宽字形为主，影响可控 |
| egui 处于 0.x，存在破坏性变更 | 高 | 锁定精确版本，升级走独立 PR 加全量回归 |
| 观感是自绘风格，不是系统原生控件 | 低 | 对终端这类自绘界面反而是优点：跨平台观感完全一致 |

最后一条需要说明清楚：egui 的观感是「自绘的一致」，不是「跟随系统原生控件」。这个区别在对外描述时不要混淆。

### 复查触发条件

1. egui 某次升级出现无法绕过的输入法回归，且降级不可行；
2. 终端控件层的实际投入明显超出估算，说明「自研 vs 找现成控件」的前提需要重估；
3. 出现明确的采购方要求「系统原生控件 + 无障碍合规」。

## 备选方案与否决理由

| 方案 | 否决理由 |
|---|---|
| Tauri 2 + 前端终端组件（ADR-0002） | 保留为历史记录。否决原因：WebView 输入法不可控，跨平台内核差异需要长期维护 |
| Qt / C++ | 许可与工程复杂度；且与「用 Rust 重写」的立项前提冲突 |
| iced | 保留模式架构，终端这种高频重绘场景反而更绕；生态小于 egui |
| Flutter / Slint | 引入第二语言与工具链；终端控件仍要自研 |
