# 凭据与安全设计

本文写凭据与安全相关能力的**实现结构与取舍**，不重复用户操作步骤；用户视角的
安全模型见 [security.md](../security.md)。密钥、口令、token 都不进入源码仓库。

## 这一层负责什么、不负责什么

| 这一层负责 | 这一层不负责 |
|---|---|
| 保险库的字节格式、加密与解密 | 文件放在哪里、什么时候写盘（调用方决定） |
| 会话库只存引用、不存明文 | 会话本身能不能连上（连接层的事） |
| 锁屏状态机与主密码复用 | 操作系统账户安全、磁盘加密 |
| `term-desk serve` 的准入握手 | 远程访问方案（只监听回环） |

## 保险库的边界

`term-vault` 只做一件事：把一组凭据变成可解密的文件字节，再把字节还原成凭据。
三条刻意的边界：

- **不管 IO**。`seal()` 返回 `Vec<u8>`，写哪个文件、什么时候写由调用方决定。
- **不管 UI**。没有「输入密码」的循环，也没有重试次数；错误分类交给上层。
- **没有运行时**。同步、无线程、无 `tokio`，依赖表里只有加密库与序列化。

条目有三类：密码、私钥（可带口令）、代理凭据（用户名 + 口令）。`kind` 只
区分用途，保险库不建立「哪条会话用哪条凭据」的反向引用——那由会话库的
`vault_entry_id` 记录。

解锁态下条目在内存里是明文，这是必然的；能做的是 `lock()` 与 `Drop` 时就地
清零并释放。锁定态下条目为空，任何写入返回 `Locked`。

## 文件格式与 AAD

文件是「前缀 + header + 密文」：

```
偏移  长度  内容
0     6     magic "ZTVLT\0"
6     1     版本
7     1     保留
8     4     header 长度（小端 u32）
12    N     header（UTF-8 JSON：KDF 参数 / AEAD 参数 / 可选提示）
12+N  M     密文（末尾自带 16 字节 tag）
```

关键设计：**密文之前的整段字节就是 AAD**。header 里的 Argon2 参数、AEAD 算法与
nonce 都因此被绑进认证范围：把内存开销从 64 MiB 改成 8 MiB 再离线爆破，AEAD
校验会直接失败。比起「参数写在旁边、信任它」，这条不花额外成本。

`header` 里不存创建时间：时间戳不是安全属性（可伪造），却会让测试依赖时钟；
要审计「什么时候建的」看文件 mtime。主密码提示以明文存在 header 里，故意如此
——它是忘了密码时唯一的线索，所以界面与文档都要说清「不要往里写密码本身」。

## 密钥派生与加密

| 项 | 取值 | 说明 |
|---|---|---|
| KDF | Argon2id | 参数写在 header，参与 AAD |
| 内存 / 迭代 / 并行 | 64 MiB / 3 / 4 | 生产参数的下限；本机解锁约数百毫秒 |
| 盐 | 16 字节随机 | 每次改主密码换新盐 |
| 密钥 | 32 字节 | 派生结果用零化容器持有 |
| AEAD | XChaCha20-Poly1305 | 24 字节 nonce，每次 `seal` 换新 |

`unlock` 不区分「密码错」与「文件被改过」：AEAD 本身也区分不了，两者都报同一个
认证失败。版本高于程序支持、算法不认识则单独报「不支持」，因为那是可行动的
信息（升级程序或换文件），与「密码不对」不是一件事。

`seal` 每次都生成新 nonce，同样的条目两次加密结果不同。nonce 必须先写进
header 再算 AAD，顺序反了就会用旧 nonce 加密、用新 nonce 解密。

## 换主密码

`change_password` 只做三件事：换盐、按新口令重新派生、替换 header 里的 KDF
参数。条目内容不变，不需要重新加密一遍明文之外的任何东西。

调用方必须紧接着 `seal()` 落盘：内存里的密钥已经换成新的，磁盘上还是旧口令
加密的旧文件。这个顺序不能由保险库替调用方保证，因为「什么时候写、写失败怎么
办」是应用策略。

## 密码的三种保存策略

| 策略 | 凭据留在哪里 | 生命周期 | 代价 |
|---|---|---|---|
| 不记住 | 本次连接的内存 | 连接结束即忘 | 每次重连都要重输 |
| 本次记住 | 进程内存 | 进程退出即忘 | 不需要主密码，也不落盘 |
| 永久记住 | 保险库 | 跨启动 | 需要主密码解锁 |

实现落点：

- 对话框里的密码默认只用于本次连接，输入框提示「不写盘」。连接提交时值被
  取走交给连接层，界面不再保留。
- 「存入保险库」只在保险库已解锁时可用；锁着时勾选框禁用并提示先去解锁。
- 存密码的顺序是**先落会话列表、再写引用**：引用是一次 `UPDATE`，行不在就
  什么都不会发生。写保险库失败不拦这次连接——密码就在手上，连上比「记住它」
  更重要，错误留在属性页。
- 会话库只记条目 id，条目 id 默认与会话名一致；保存列表时按会话名匹配并保留
  引用，因此改名不会自动把引用带过去。静默迁移会让「我改了名，密码却跟过去
  了」无从解释，当前行为是改名后重新保存一次密码。

## 登录方案与保险库的边界

可复用的登录方案（见
[01-sessions-and-connection.md](01-sessions-and-connection.md) 的「登录方案与统一解析」）
存放在偏好设置里，不存放在保险库里。它持有的是可复用配置——用户名、私钥位置、
键盘交互应答表——不是口令密文；保险库仍然只管「哪条会话对应哪条密码」。两者的
分工刻意保持清楚：

- **方案带得进用户名与私钥，带不进密码**。系统 `ssh` 不接受非交互密码，走那条
  路径时密码只能手敲；内置 SSH 才是「方案覆盖配置 → 保险库补密码 → 必要时弹框」
  的三段回退。
- **方案表进偏好设置，密码引用进会话库**。方案是可编辑的数据表，改完要立即生效；
  密码引用与会话身份绑在一起。把它们放进不同的存储，是为了让「改方案影响所有引用
  它的会话」与「改会话只影响自己」各自成立。
- **控制面不认识保险库**。方案解析发生在 `term-session`，它按方案覆盖配置后把结果
  交出去；解锁保险库、取密码是应用层的职责。于是一条无窗口路径（脚本 / 桥接）需要
  密码时，仍要由应用层解锁，控制面不会替它读保险库。

## 会话库与凭据引用

会话库是 SQLite，表结构是「身份列 + 整份 JSON」：

| 列 | 用途 |
|---|---|
| `name` / `group_name` / `protocol` / `host` / `port` / `username` | 会话树要直接查询的身份信息 |
| `vault_entry_id` | 密码在保险库里的条目 id，**永远不是密码本身** |
| `config` | `SessionConfig` 的完整 JSON |
| `position` | 展示顺序 |

`vault_entry_id` 单独一列而不进 JSON，是因为它是「密码在哪」的唯一记录点，
必须能在**不解锁保险库**时被读出来。`load()` 因此不需要保险库：会话列表照常
可读，连接时才要求解锁。

`save()` 全量重写会话列表，但会保留每条的 `vault_entry_id`——保存列表不该把
密码引用抹掉。库以 `name` 为主键，重名在写入前就已被上层消解。测试会检查库
文件（含 WAL）的原始字节里不出现明文口令。

## 已知主机

默认账本是 `~/.ssh/known_hosts`，也可以显式指定路径。写入只记「主机 token +
公钥本体」，注释被去掉：注释是给人看的自由文本，写进账本只会让下一个人以为
那行有特别含义。非默认端口写成 `[host]:port`。

维护面提供列举、遗忘、换钥三个动作，原则是**只动被命中的行**：

- 不认识的行走原样保留（注释、空行、`@cert-authority`、带 `!` 的反向匹配、
  哈希行），因为这是用户与 OpenSSH 共用的文件。
- 遗忘只做精确匹配，不删通配符覆盖的行，也不删同主机的其他端口。
- 没命中就一个字节都不写，连 mtime 都不动，避免备份脚本看到假变更。
- 写文件走「同目录临时文件 + rename」，中途崩掉时旧文件还在。

## 锁屏状态机

状态只有两个字段：锁没锁、上一次密码对不对。密码本身不进视图状态，输入框用
跨帧缓冲持有，提交后立刻清空。状态迁移：

| 动作 | 结果 |
|---|---|
| `Lock` | 锁定并清错误 |
| `Unlock` | 解锁并清错误 |
| `Failed` | 保持锁定，标记密码错误 |
| `Cancel` | 仅在「尚未创建保险库」时允许，作为逃生口 |

解锁复用保险库主密码，没有第二套口令体系：有库就对文件做一次 `Vault::unlock`，
成功后把解开的库重新挂回内存；没库则允许当场创建主密码，或者取消离开。
「没有主密码却把所有出口都封死」是比不做锁屏更糟的形态，所以逃生口只存在于
无库这一种情况：锁屏界面本身只保留蓝色标题与密码框，无库时
用 `Esc` 触发 `Cancel`，有库时不提供可见的「不输密码就走」入口。

锁屏也会影响无窗口入口：`term-desk serve` 在锁屏期间把每次调用都变成 `locked`
错误，而不主动断开连接——客户端可能只是暂时拿不到结果，等用户回来解锁再继续。

## 会话日志的清洗

日志默认关闭。开启后有两种模式：可打印文本（默认）与原始字节。文本模式不是
简单过滤，而是复用与主终端同一个 VT 解析器：

- 转义序列、光标定位、窗口标题（OSC）被吃掉，不进文件；
- `\r` 一律当换行，`\r\n` 只算一个；进度条那种「回行首重画」在纯文本里最自然
  的形态就是多行，丢掉 `\r` 反而会让同一行被反复追加成超长文本；
- 退格、响铃等其余控制字符直接丢弃；
- 转义序列跨 chunk 的状态由解析器保留，UTF-8 半截字符也由它拼完整再交出，
  中文输出被读边界切开不会变成乱码。

原始字节模式保留转义序列，供用户明确要求回放时使用；文件头会写一行说明，
区分两种模式。文件名按模板展开并做安全化：目录分隔符与 NUL 折成 `-`，控制
字符丢掉，去首尾空白并限长，保证一个手滑的会话名不会把文件写到目录外。

日志是**明文**，这是设计选择而不是遗漏：它的用途是事后 `grep`，加密会让
`grep`、`tail -f`、归档全部失效。默认关闭、开启时明确告知，是这里的边界。

## term-desk serve 的准入

`term-desk serve` 把能力面暴露到本机 TCP，准入分三层：

1. **只绑回环**。没有 `--host` 参数是刻意的；要远程访问请走 SSH 隧道，那是
   已被审计的通道。把能力面直接挂到 `0.0.0.0` 等于把终端交给局域网。
2. **token 文件**。默认在 `~/.zterm/bridge.token`，首次以 `0600` 生成；权限宽于 `0600`
   就拒绝启动，且**不擅自 chmod**——那会掩盖用户自己设的 ACL 意图。文件用
   `create_new` 创建，不覆盖已有 token；服务重启不该让已配置的客户端全部失效。
   token 是 32 字节随机数的 64 个 hex 字符；比对逐字节累加，不提前返回。
3. **一次性握手**。每条连接的第一条请求必须是 `auth`，token 不对就回一个
   `locked`（`-32003`）错误并关闭连接，只给一次机会；之后每次能力面调用前
   再问一次锁屏（纵深防御），但**不主动断连接**——断不断由客户端决定。

锁屏探测只有 macOS 有实现（读 `ioreg`）；其他平台返回「不知道」，此时放行，
主闸门仍是 token。这个选择会让「探测失败」不再无声：生产路径会累加计数并写
一条 stderr 审计行。`desk serve` 与 GUI 是两个进程，各自持有自己的会话池，
通过 `serve` 打开的标签不会出现在正在运行的窗口里——这是当前明确承认的限制。

## 设计约束与边界

- 不提供主密码找回：忘记主密码即无法解密，保险库里没有后门，也没有第二把
  恢复钥匙。这是加密格式的直接后果。
- 不把凭据写进会话配置、偏好、布局或命令行参数；token 也不进环境变量和
  `ps` 可见的参数列表。
- 不在锁屏或保险库锁定时静默放行任何凭据读写：要么解锁，要么明确报错。
- 不宣称跨平台锁屏防护：没有实现的平台不假装知道，也不假装锁着。
- 不加密会话日志，也不把它伪装成安全存储；它默认关闭，开启后是明文文本。
- 不与云服务同步凭据；本地优先是安全模型的一部分，不只是产品取舍。
