# tmux 集成

本文说明 WindTerm 怎样读 `tmux -CC` 的控制模式输出、把它变成一组可消费的事件，以及本地界面与远端 tmux 结构之间的边界：哪些是解析事实、哪些是本地动作、遇到不认识的指令时为什么必须原样透传而不是吞掉。

**负责**：控制模式的字节旁路与行分帧、事件模型、八进制转义的还原、解析状态机与降级路径、布局字符串与窗格集合的记录方式、反向控制命令的生成与下发闸门、控制模式面板、detach 与重新进入的边界。

**不负责**：tmux 自身的会话管理语义（远端程序的行为由它自己定义）；本地分屏树的布局算法（见《标签、分屏与布局持久化》）；OSC 133 命令块的解析（只在面板里被读取展示）；终端渲染与滚动（见《终端核心与渲染》）。

## 1. 字节从哪来：非破坏性旁路

控制模式的输出仍然是这条会话的普通输出。本地对它的处理是**复制一份**来做解析，而不是把字节从显示路径里截走：

- 会话线程照常把字节喂给 VT，屏幕照常前进、日志照常记录。
- UI 每帧把本帧收到的字节再喂给本标签自己的控制模式状态机。

所以解析是**旁路**，不是过滤器。这个选择带来一条必须承认的性质：被识别出来的控制行**不会**从屏幕上消失——VT 已经收过它们了。真正的「把控制行摘掉」需要改写显示路径，那是另一类改动，不在本设计的范围内。

分帧按字节做，不按字符做：控制行可能被任意切开（`%be` 与 `gin …` 分属两块），所以每个标签维护一段跨块缓冲，攒到 `\n` 才算一行；行尾的 `\r` 一并剥掉，免得 `%begin` 后面那个回车把指令名粘成 `%begin\r`；空行跳过。用宽松解码处理非 UTF-8 字节——控制行本身是 ASCII，但同一条流里可能夹着用户程序的输出。

状态机挂在**标签**上，不是窗口上。窗口级单例会串线：A 标签在跑 tmux，B 标签却被判定为 `active`，反向命令就会注进 B 的 shell。

## 2. 事件模型

一行控制输出解析成一条事件，`data` 里的转义已经还原成原始字节：

| 事件 | 触发行 | 携带 |
|---|---|---|
| `Begin` / `End` | `%begin` / `%end` | 时间戳、命令序号（标志位不保留） |
| `Output` | `%output` | 窗格号、已还原的字节 |
| `LayoutChange` | `%layout-change` | 窗口号、**当前**布局字符串 |
| `WindowAdd` / `WindowClose` / `WindowRenamed` | `%window-*` | 窗口号，重命名还带名字 |
| `SessionChanged` | `%session-changed` | 会话号与名字 |
| `PaneModeChanged` | `%pane-mode-changed` | 窗格号 |
| `Pause` / `Continue` | `%pause` / `%continue` | 无 |
| `ClientDetached` | `%client-detached` | 客户端名 |
| `Exit` | `%exit` | 原因文本 |
| `Passthrough` | 其它一切 | 原行 |

`%layout-change` 的真实输出带三个布局字段：当前布局、旧布局、激活标记。**只取第一个**——后两个不是当前事实，取错会让本地布局慢一拍。

`%begin` / `%end` 只标「一段命令回显的开始与结束」，不改变窗格数据的处理方式：块内的 `%output` 与块外的同样处理。把「在通知块里」当成「才处理输出」会漏掉 tmux 主动推送的那部分。

## 3. 八进制转义还原

`%output` 的数据段把控制字节写成 `\ooo`（三个八进制数字），其中最常见的是回车与换行。还原是纯字节操作：

- 扫描到反斜杠且后面恰好跟三个八进制数字，就合成一个字节并前进四格；
- 否则原样留下这个字节，前进一格。

三条边界要写清：

- **只在数据段做**，不对整行做。整行还原会把指令名里的字面反斜杠也吃掉。
- **不解释其它转义**。`\n` 这类写法在 tmux 的数据段里不是换行，把它当换行是替对端猜语义。
- **结果是字节而不是字符串**。窗格输出可以是任意二进制（粘贴、鼠标上报、压缩流），先转成 `String` 会在非 UTF-8 处丢字节。

## 4. 解析状态机

状态只有五项事实：是否在控制模式、是否在通知块里、见过哪些窗格、最近一次布局字符串、是否已退出。

```
Idle ──%begin / %output / %layout-change / %window-* / %session-changed / %pane-mode-changed──► Active
Active ──%exit──► Idle（exited = true）
```

四条判定值得单独说：

- **`active` 只由「确实是控制模式的事实」置位**。`%pause` / `%continue` 是流控开关，`%client-detached` 说的是**别的**客户端断开——三者都不代表本次控制模式还活着，所以不动 `active`。
- **真正的结束只认 `%exit`**。把 `%client-detached` 当成结束，会在自己还没退出时就把界面切回普通终端。
- **退出后 `active = false` 且 `exited = true`**，同时清掉「在通知块里」。`exited` 是「最近一次退出」的记账，不是永久锁：同一条标签再次收到 `%begin` 时仍会重新置 `active`，所以重新 attach 不需要新建状态机。
- **数字解析失败一律取 0，不 panic**。控制行是不可信输入，一个畸形的窗格号不该让整个界面挂掉；0 会让后续动作指向一个不存在的窗格，界面上表现为「点了没反应」，比崩溃好。

## 5. 未知指令与解析失败：一律 Passthrough

这条是全文最重要的安全语义：**控制模式不是一直开着的**。

- 不以 `%` 开头的行 → `Passthrough`，原样交回。
- 以 `%` 开头但指令名不认识 → `Passthrough`，原样交回。
- 一行里字段不够、数字畸形 → 仍产出对应事件（缺省 0），不抛错、不中断。

理由很直接：解析失败时用户仍然要看到 shell 的输出。吞掉一行不可识别的控制输出，症状是「屏幕上少了一段」——用户既不知道少了什么，也不知道是终端的问题还是远端程序的问题。原样透传最坏的结果是「多显示了一行协议文本」，那是可诊断的。

首行还有一个特殊情形：tmux 进入控制模式前会先发一个 DCS 前导（`ESC P 1000 p`），它没有终止符，会**粘在**第一条 `%begin` 前面。所以解析前先尝试剥掉这个前导，但**只在剥掉之后确实以 `%` 开头时**才采用剥后的结果；否则整行原样透传，免得把用户程序自己输出的 ESC 序列吃掉。

## 6. 本地布局映射

解析层记录两样东西：窗格号集合（见过的 `%output` 与 `%pane-mode-changed` 里的号）与最近一次布局字符串。

**只记录，不重排**。控制模式不改写本地分屏树，这条是刻意的边界：

- 布局字符串是 tmux 的格子语法，把它翻译成本地树需要一整套换算（单元格、边框、状态行占位），而本地树的写入口是唯一的（派发布局动作），从解析器直接写会造出第二条写路径。
- 「本地拖拽」与「远端布局」谁是真源必须先定。两头都能写，用户拖一下、远端又推一次，界面会来回跳。
- 记录下来的布局是**事实**，面板据此显示「远端现在是什么形状」；要把它变成可操作的结构，得先定义「本地拖拽与远端推送谁说了算」的仲裁规则，那是独立的一步。

窗格集合的用途是「这条会话里出现过哪些 pane」，用于面板显示与反向命令的目标校验。它不去重命名、不排序、不假设号是连续的。

## 7. 反向控制

本地发给 tmux 的是**控制命令的文本行**，枚举里每个变体负责生成一行：

- 分屏、选窗格、关窗格、开窗口、选窗口、改名、detach、刷新、改变客户端尺寸；
- 向某个窗格发文本，或发原始字节。

生成阶段就把安全性做完，调用方不需要也不应该再拼一次：

- **文本走字面发送**，参数总是加双引号；引号与反斜杠转义。不加引号时，空格会把内容拆成多个按键，`;` 会被 tmux 当成命令分隔符——那是注入面。
- **含控制字符的文本退到十六进制路径**。换行本身就是命令分隔符，不能出现在一条控制命令里。
- **二进制走逐字节十六进制**。这样不会在 UTF-8 边界上被截断或替换，也无从注入。
- **窗口名先抹掉控制字符**，再按需加引号。换行会截断一条控制命令，等于注入；窗口名没有「合法控制字符」这回事。
- **只有真的需要才加引号**，保持 `rename-window prod` 这种可读形式；单引号也算需要，因为 tmux 的命令行里它同样是引号。

下发有两个硬闸：

1. **控制模式没开就一条不发**。用户没 attach、却从面板点了分屏，命令会直接注进正在跑的交互 shell。宁可「点了没反应」，也不能「点了有坏处」。
2. **裸写，不走粘贴路径**。控制命令是协议字节，不是用户文本。走粘贴编码会把命令包进括号粘贴并把换行归一成回车，tmux 认不得，命令就变成一次粘贴回显进了 shell。这正是「本地到远端的控制」必须从普通粘贴里分出来的原因。

闸门读的是**活动标签**的状态：越界或没有活动标签一律不发，免得 A 标签在跑 tmux 却把控制行注进 B 标签。

## 8. 面板

控制模式面板是一个独立浮窗，默认关闭，由「窗格」菜单里的开关翻 `ViewState` 的对应位；关掉窗口会把开关翻回去，再点菜单能重开。

面板上有四块内容：

- **状态行**：`Control mode: active / idle`、见过的窗格号、最近一次布局字符串（空时显示占位符）。
- **喂行输入框**：输入一行控制输出、回车解析，结果显示在日志里。这条入口用于「手上有一段抓包，想看解析成什么」，不需要真的跑 tmux。
- **反向控制按钮**：水平分屏、垂直分屏、detach。按钮只生成命令，实际写入由窗口层做。
- **日志**：最近若干条解析结果，环形保留（超过上限丢最旧的一条）。
- **命令块**：OSC 133 索引出的命令块，显示序号、字节范围、退出码与是否在跑。

喂行有两个来源，彼此独立：面板输入框喂的是**手输的一行**，会话字节流喂的是**自动解析**。前者不会与后者重复喂同一行，因为自动那条走的是 tap 的字节缓冲。

面板不做「假 attach」：它显示的是解析结果与本地动作入口，不声称自己已经和远端建立了可交互的窗格映射。

## 9. detach 与重新进入

三种「结束」要分清：

| 现象 | 含义 | 本地反应 |
|---|---|---|
| 用户点 detach | 本地主动让远端把本客户端摘掉 | 发 `detach-client`；远端会话保留 |
| `%client-detached` | **别的**客户端断开 | 什么都不做，控制模式仍活着 |
| `%exit` | 本次控制模式结束 | `active = false`、`exited = true`，界面回普通终端 |

detach 不销毁远端会话：tmux 的语义是「客户端走了，会话还在」。本地的边界是——**不做自动重连**。重新进入就是再执行一次 `tmux -CC attach`；同一条标签再收到 `%begin` 时状态机会重新置 `active`，所以不需要重建对象。自动重连要回答「多久重试、失败几次放弃、期间界面显示什么」，这些问题没有用户可接受的默认答案，因此不默认做。

断开会话（SSH 断了）与 `%exit` 是两件事：前者由会话层报 `Closed`，后者是 tmux 的正常收场。两者都回到「非控制模式」，但原因要分开告诉用户。

## 10. 与分屏、标签模型的关系

本地模型有两级：标签（一条会话）与窗格（一块终端区域）。tmux 的模型有三到四级：会话、窗口、窗格，且都在远端。

对应关系刻意**不是 1:1**：

- **一个本地标签承载一次控制模式连接**。控制模式的状态属于标签，因为字节属于那条会话。
- **tmux 的窗格不是本地窗格**。本地窗格是布局树的叶子，有自己的矩形与焦点；tmux 的窗格是远端结构，本地只记录它的号与输出。
- **不把 tmux 结构塞进本地标签栏**。那会让「关标签」同时意味着「关远端窗口」还是「只关本地视图」变成歧义；远端的增删由 tmux 自己决定，本地只反映。
- **反向动作的目标是窗格号**，不是本地叶子下标。混用两种编号，在分屏顺序变化后就会打错窗格。

因此这里的定位是：**解析与展示是本地能力，结构真源仍在远端**。本地能做的动作只有「发一条控制命令」，不做「本地先改、再通知远端」——后者在远端拒绝时无法回滚。

## 11. 边界

- **控制模式不改写本地分屏树**；布局字符串只作为事实记录与展示。
- **解析是旁路，不是过滤器**：识别出的控制行仍会经过 VT，不会从屏幕消失。
- **未知指令与解析失败一律透传**，不吞、不猜、不中断。
- **数字字段解析失败取 0**，不 panic；后续动作指向不存在的窗格时表现为无反应。
- **只有 `%exit` 结束控制模式**；流控与「别的客户端断开」不改状态。
- **反向命令的注入面在生成阶段封死**：引号、控制字符、二进制三条路径各自有明确处理，调用方不再二次拼接。
- **控制模式未开时一条命令都不发**；闸门读活动标签，不读窗口级单例。
- **不做自动重连**，也不假装 attach：面板展示解析结果与动作入口，不宣称已有可交互的远端窗格映射。
