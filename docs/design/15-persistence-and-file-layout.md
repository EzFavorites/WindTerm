# 持久化与文件布局

本文说明所有落盘文件共同依赖的那层基础设施：文件放在哪、怎么原子地写、旧格式
怎么收口、各模块的文件各管什么。它横切会话库、保险库、偏好、布局与会话日志——
这些模块各自的内容格式见对应篇目，本篇只讲它们脚下的地基。

**负责**：profile 目录的唯一解析、启动期的一次性整理、原子写的命名与清理规则、
档案层的依赖边界、各文件的职责分工。

**不负责**：任何文件的**内容格式**（会话库见[会话与连接](01-sessions-and-connection.md)与
[凭据与安全](06-security-credentials.md)，布局见[标签分屏](04-tabs-split-layout.md)，
日志清洗见[凭据与安全](06-security-credentials.md)）；加密与解密（[06](06-security-credentials.md)）；
崩溃后的恢复流程（[10](10-crash-hardening.md)）。

## 为什么路径规则要单独一层

一个只有一条实质规则的小模块值得独立成 crate，是因为它解决的是**依赖方向**问题：
多个模块都需要知道"文件写在哪"——会话日志、偏好、会话库、保险库、布局。如果各模块
自己算，同一条规则会散成多份；如果把目录解析塞进持久化层，会话日志那边为了知道
写哪儿就得反过来依赖带 SQLite 的持久化层，依赖就成环了。

于是把这条规则提到所有消费者**之下**：路径层只依赖一个取平台配置目录的库，持久化层
与 IO 层都依赖它，彼此不依赖。它只回答"目录在哪"，不回答"目录里有什么"——后者是
各模块自己的知识，新增一个文件不该改这个 crate。

## 一个子目录，而不是平铺

profile 目录是平台配置目录下的一个固定子目录；会话库、保险库、偏好、布局、日志、
用户脚本都在它下面。收进单一子目录的理由很实际：用户要整体备份或搬走配置时，只有
一个目录要处理，不会和别的应用在配置根下抢位置。

同时提供一个环境变量覆盖入口，把整个 profile 目录重定向到别处。它有三类用途：测试
用一次性目录、截图夹具、以及"带一份配置走"的便携场景。这些场合既不该读用户的真实
数据，更不该往真实目录写，所以覆盖存在时，启动期整理整体跳过（见下）。

## 启动期的一次性整理

目录规则改过一次：早期直接把文件平铺在配置根下，后来收进子目录。为了让已有用户无感，
启动时做一次整理，两件事都只做"加法"与"删自己写坏的东西"：

- **搬迁**：把旧位置的一份名单文件复制到新目录，**只在目标不存在时**复制。复制走
  "先写临时名再改名"，中途失败不会留下一个看起来完整的半截库。名单涵盖会话库及其
  SQLite 旁路文件、偏好、布局、保险库，以及更早的一份明文会话格式；用户脚本目录也一并
  搬（只搬顶层普通文件，不跟软链）。**旧文件原地不动**，何时清理由用户决定——自动删掉
  用户可能还当成备份的东西，比留一份副本更糟。
- **清理**：删掉原子写残留的临时文件，但只认自己写坏的东西——带本应用前缀、且是一小时
  之前的。更短的不删，因为另一个正在运行的实例可能还在用它。在旧位置（那是与别的应用
  共享的目录）清理时只认自己那几类前缀，绝不按"所有临时文件"批量删。

覆盖环境变量在场时这两步都跳过：它指向的多半是一次性目录，既没有旧数据可搬，也不该
往真实目录里写。

## 原子写与多进程

所有需要改写整个文件的模块都走同一条规则：在**同目录**写一个临时文件，写完 `rename`
覆盖目标。同目录是为了让 `rename` 保持原子；跨文件系统会退化成复制加删除，中途断电
就留下半截文件。

临时文件名必须唯一。固定名字在单进程串行时没问题，但产品可以开多个窗口，也就是多个
进程共享同一份 profile 目录：两个进程交错写盘时，A 的改名可能覆盖掉 B 刚写好的临时文件。
因此临时名由进程标识、时间戳与进程内序号拼成，且不引入新依赖；改名失败时主动删掉临时
文件，目录里不留半截账本。

## 档案层的边界

档案层是"配置目录里的东西怎么读、怎么写"，它的全部副作用就是读写这些文件：

| 有 | 没有 |
|---|---|
| 纯语义层、路径层、SQLite 会话库、序列化 | 伪终端、系统信号库、异步运行时、任何界面框架 |

它起不了线程、开不了伪终端、连不上网。这条边界让"改一行偏好"不必等会话监管那部分
重新编译。搜索的引擎表也放在这一层——它不是持久化，但它是偏好页的数据，菜单的在线
搜索命令与设置页必须读同一份表，放这里那条依赖就是同 crate 内部的，不产生跨层边。

一条底线贯穿整层：**读不出来不等于可以覆盖它**。配置文件是用户可能手改的，少一个逗号
不能让整份配置被默认值盖掉。读失败就是读失败，要么明确报错，要么保留原文件不动。

## 目录里有什么

文件名是各模块自己的知识，但分工要写清楚，避免两处都以为自己负责：

| 文件 | 内容 | 谁定义格式 |
|---|---|---|
| 会话库 | 会话列表与凭据引用 | 会话库 crate；档案层只定位文件 |
| 保险库 | 加密后的凭据 | 保险库 crate；档案层只读写字节 |
| 偏好 | 语言、字体、光标、粘贴确认等界面偏好 | 档案层 |
| 布局 | 标签、分屏、停靠结构，以及文件自身的写盘时间/退出形态 | 档案层 |
| 快捷栏 | 快捷命令条目 | 档案层 |
| 在线搜索表 | 引擎名与 URL 模板 | 档案层 |
| 命令历史 | 历史命令 | 档案层 |
| 会话日志 | 可打印文本或原始字节，默认关闭 | IO 层；档案层只提供目录 |

会话库只有一种格式：更早的明文会话文件已不再读取。好处是读失败就是读失败，不存在
"半迁移"的中间状态。保险库的扩展名是自造的，用来把它和普通数据文件区分开。

## 文件属性与语义字段分开

布局文件带一个 schema 版本，读盘时先校验：比自己新的版本直接拒绝，降级成一条默认
会话，而不是硬读一份自己看不懂的结构。版本号是**文件的属性**，不进布局结构体——
塞进去就要在每个构造点写一个自己并没有意见的数字，而某个点写成旧值就会让文件带着
错的版本落盘。

同理，最近一次写盘时间与上次退出形态也和布局结构分开存放：它们回答"这份文件什么时候
写的、上次是不是正常退出"，不是"窗口长什么样"。两者关注点不同，而且布局那部分已经
不小，再塞进来会顶到单文件行数上限。对调用方仍只暴露一个入口——这些名字在布局模块里
再导出了一遍。

时间以字符串记录退出形态而非枚举：将来多一种形态时，老程序仍能读出整份文件。非正常
退出只在很短的一段时效窗口内提示用户——很久以前的一次崩溃与今天的启动无关，弹出来
只是噪音。

## 设计约束

- 路径只有一个出处；搬迁与清理都从这里拿"旧位置"，不在别处重复计算。
- 新增落盘文件必须同步进搬迁名单与临时文件前缀清单，否则搬迁与清理都会漏掉它。
- 原子写用唯一临时名；多进程共享目录时固定名字会互相覆盖。
- 配置文件读失败不静默覆盖；单一格式，不留半迁移状态。
- 文件属性（版本、时间、退出形态）与语义结构分开；会漂移的数字不写死在代码注释或文档里。
