# 主题与视觉基线

本文说明颜色与尺寸从哪来、怎么组织、怎么被消费，以及「改动有没有把界面画歪」这件事靠什么守住。

**负责**：调色板数据结构与扩展色解析、内置配色方案、主题文件的解析与回退、边栏取色为何独立于配色方案、外部配色方案的导入边界、字号与行高、控件尺寸与描边口径、截图基线机制、已知视觉边界。

**不负责**：终端网格如何存颜色（见《终端核心与渲染》）；控件布局与交互（见各功能文档）；渲染管线与叠层顺序（见《终端核心与渲染》第 7 节）。

## 1. 三层色源，各管一件事

界面上的颜色不允许随手写。色值与尺寸令牌集中在 `crates/term-core/src/theme.rs`（外壳适配层只做类型转换、安装视觉样式，以及补齐少数由绘制框架语义决定的底色），按用途分成三组，互不代管：

| 组 | 内容 | 归属 |
|---|---|---|
| **终端调色板** `Palette` | 16 色 ANSI、默认前景 / 背景、色源说明 | 只描述终端内容；由网格绘制读取 |
| **外壳色** `CHROME_*` / `DESIGN_TOKENS` / `CHROME_SCALE` | 面板底、弹窗底、控件表面、文字灰阶、边框 | 只描述 chrome；终端调色板不参与控件配色 |
| **点缀色** `QUICK_BAR` / `SESSION_TREE` / `MARGIN` | 快捷栏四组标记、会话树图标、边栏五列 | 只描述「小图形」或「栏位」；不铺面积 |

分三组不是分类癖：把弹窗底、选中态、输入框底各用一套来源，会在同一张弹窗里出现三个互不协调的灰阶。所以控件表面被收成**一条中性灰阶**（`CHROME_SCALE`），饱和色只留给焦点。

`ACCENT_BLUE` 是刻意共享的单一值：菜单选中块、活动标签顶部蓝线、「隧道」开关的开态、查找命中时整条状态栏的染色共用它。四处共用一个常量而不是四个近似值——否则调一处，另外三处看起来就像「差了一点」。

## 2. 调色板与扩展色

```rust
pub struct Palette {
    pub ansi: [Rgb; 16],
    pub default_fg: Rgb,
    pub default_bg: Rgb,
    pub ansi_source: String,   // 色源说明：来自文件，或内置回退
    pub theme_name: String,
}
```

16 色之外还有 240 项按 xterm-256 规则算出来，不单独存表：

- `0..=15` 直接取 `ansi`；
- `16..=231` 是 6×6×6 色立方，每级映射 `0 → 0`，其余 `55 + v × 40`；
- `232..=255` 是 24 级灰阶，`8 + (i − 232) × 10`。

于是网格里只需要三种颜色表达：`Default`（跟随当前调色板的默认前景 / 背景）、`Indexed(u8)`（256 色之一）、`Rgb`（SGR 直给的真彩色）。绘制时一个纯函数 `resolve(palette, colour, is_fg)` 统一解析，UI 因此不必持有终端实例，只依赖快照。

颜色类型转换只有一个点：`apps/desktop/src/theme.rs::to_color32`。语义层永远不认识绘制框架的颜色类型，换后端时改这一处。

## 3. 主题文件与内置方案

**主题文件**是带 `//` 注释的 JSON：解析前先剥注释（字符串内的 `//` 不算），再按 `styles` 数组找 16 个约定名（`terminal.ansiBlack` … `terminal.ansiBrightWhite`）与 `text.default`。

- 16 项必须**全部**找到，否则整份判失败并回退——半个调色板比没有调色板更危险；
- 颜色接受 `#RRGGBB` 与 `#AARRGGBB`（带前导 alpha 的写法只取低 24 位）；
- `text.default` 缺项时只回退该项，不影响 16 色。

回退不是静默的：`ansi_source` 会写成 `built-in defaults (theme file not found)` 这个约定字符串，自检命令与排障都能说出「颜色来自文件还是回退」。判断它的人不止一个，所以这个字符串是公开常量，不是内联字面量。

**内置方案**有七个（`cmd` / `dumb` / `linux` / `macos` / `none` / `powershell` / `routeros`），每个只有 16 色加前景；背景统一为黑——配色方案定义的是「终端内容色」，不是窗口底色。两项刻意复用：`powershell` 用 `cmd` 的调色板，`routeros` 用 `linux` 的，因为对应的终端类型本来就共用同一套 16 色。`dumb` 是灰阶，代表哑终端没有彩色能力。

运行期切换方案只换 `Palette`（网格用色），**不动**外壳色与边栏色。这一点由数据结构保证：`apply_ui_style` 的签名虽然收 `palette`，但控件配色全部来自 `CHROME_SCALE` 与尺寸令牌。

## 4. 边栏取色为何独立

终端左侧边栏（时间戳、行号、提示符 / 续行符号、当前行底色）有自己的一套颜色，不来自 16 色 ANSI，也不跟随配色方案。

理由只有一句：**边栏属于外壳，不属于终端内容**。用户换配色方案是为了让远端输出更好看，若行号也跟着变，青色的行号可能正好撞上某套方案里的青色文字，边栏就从「辅助信息」变成「噪声」。反过来，边栏不随方案变化，也让「行号列宽、数字位置」这类视觉基线不受配色切换影响。

现行取值（`MARGIN`）：时间戳 `#808080`（中性灰，比正文暗一档）、行号 `#0094B2`（青）、提示符 `›` `#94E400`（绿）、续行 `~` `#13DCF2`（亮青）、当前行时间戳与行号 `#FF0091`（品红）、当前行整行底 `#282833`（偏蓝的深灰）。除时间戳外都带明确色相，用途是「一眼区分列」，而不是装饰。

## 5. 外部配色方案导入

导入的目标类型是固定的：16 色加默认前景 / 背景。Windows Terminal 的 scheme（JSON）与 iTerm2 的 `.itermcolors`（plist）提供的正是这几项，所以映射在类型上是封闭的——不存在「导进来一半」的中间形态。

导入按三步流水线划边界，且只有第二步在库内：

1. **发现**：外部配置在哪（扫哪些目录、要不要问用户、记住上次选择）。这是产品决策，刻意未实现。
2. **解析**：文本 → 领域类型。纯函数，输入是字符串，输出是 `Palette` 或「格式不认识」。用固定字符串就能单测。
3. **落库**：领域类型 → 我们的存储。要决定重名覆盖、分组映射、失败回滚，需要写权限，因此不在导入模块里。

两条硬规则写在这里，避免以后实现时走样：

- **映射不上的项必须有明确回退，不能悄悄用黑色**。缺一项就说明缺哪一项并整份拒绝，或用「当前调色板的同名项」代替并报告来源——两种都可以，静默填黑不行。
- **导入永不读密码**。导入类型里根本没有密码字段，这是类型层面的保证，不是约定。

现状：自家 `.theme` 文件的解析已经落地，内置七套方案可选；外部格式的映射属于已划好边界的未实现部分。如实反映的做法是——设置页的方案下拉只有真实存在的项，不摆假选项。

## 6. 字号与行高

终端字号默认 13.0 逻辑点（`config::DEFAULT_FONT_SIZE`），可调区间 6.0–48.0，缩放按 ±1 步进。区间的两端必须**同源**：设置页滑块、命令、渲染层、持久化四处若各写一组数，用户拖到 44 会看到 44、画成 40。

行高不单独暴露。cell 高由字体的 `row_height` 量出，cell 宽由 `glyph_width('M')` 量出——两者一起决定网格列数与 PTY 尺寸。允许单独调行高，就等于允许「网格行高」与「字形行高」两个数打架，最终一定在光标与选区上显现。

字号与字族是两件事：字号进 `FontId`，改字号不换定义，但**必须重装**——否则字形度量仍是旧的，缩放「看不出来」。字族换了才需要重新绑定定义，且因为定义下一帧才生效，度量要做两遍（详见《终端核心与渲染》第 6 节）。

UI 自己另有一套字号层级（10 / 11 / 12 / 13 / 12.2 / 14.6 逻辑点），与终端字号无关。外壳整体使用等宽字面：比例字体的墨迹中线比行中线高约 2 点，与同行图标并排时会显得「文字偏上」；等宽体的偏差在半像素内，文字与图标才共用一条中线。

## 7. 控件尺寸规范

尺寸以逻辑点计，全部来自令牌或实测常量，绘制代码里不写字面量。

**顶部三条**必须定高并垂直居中。不定高时高度由内容撑开，而横向布局是顶部对齐：同一条里高度不同的图标与文字会各自贴上沿，墨迹中线相差 2 点以上，整条看起来就是「文字偏上」。

| 条 | 高度 | 说明 |
|---|---|---|
| 菜单栏 | 32 | 含条内 1 点分隔线；由令牌 `menu_row_h − 1` 派生，不写魔数 |
| 标签条 | 30 | 活动标签块 24.5，上下各留 1.75 |
| 窗格工具行 | 26 | 拖动抓手 + 窗格动作 + 可拖走的工具栏 |

**菜单栏的横向量法**：项内边距为 0，相邻项间距 15.5。零内边距让首项墨迹落在 11 + 0.5；间距取 15.5 而不是按单项间隙反推的更小值，是因为所用等宽字面在每个词上比基线取样窄 0.5–0.7 点，把这部分补偿进间距后，十个顶级菜单的首末两端才同时对齐。左边距 11、右边距 4.5——不对称是刻意的，最右那件自带视觉体积。

菜单项常态与悬停态**无描边、无底色**，展开态才出现选中块；只清常态会让展开项单独冒出方块，比一直有框更显眼。

**底部两条等高**：状态栏与快捷命令栏都是 27.5，紧邻排列。状态栏右区字段从右往左固定顺序（产品名 / 时间 / 系统 / 行列 / 模式），字段间用 20 点空隙分区，不画竖线，不画分区色块。

**快捷命令栏**：基准字号下的内边距 8、标记宽 11、标记与文字间距 7、按钮间距 4、组间距 12、组名与组内首项间距 6、配置按钮宽 24、按钮高 22。整条按可用宽度等比缩放，下限 0.62——再窄宁可让末尾留白，也不能糊成一团。缩放时所有开销与字号同比收缩，自然宽度对缩放系数是线性的，溢出判定与绘制用同一套宽度，不会两套口径打架。

**描边口径**：控件细边框与面板之间的分隔线同为 `#444444`——用更暗的 `#2C2C2C` 画分隔线会让整窗显得「糊」；后者只留给展开中的菜单作弱描边。窗口外框是 1 点 `#444444`，圆角为 0，无阴影。终端区四周留 4 点内边距（`GRID_PAD`），滚动条宽度 15 点浮动在这条内边距之内。

**边栏列宽以 cell 宽为单位**，字体一变整体跟着变：左侧留白 0.5 格、时间戳 10 格 + 1 格、行号 3–6 格（随位数增长，最窄 3 格，否则第 10 行一出现整列右跳）、行号与符号之间 2 格、符号列 1 格、折叠标记列 1 格、右侧留白 1 格。五列全关时宽度为 0，正文回到左沿，不留一条死白。

## 8. 截图基线机制

基线是**本项目自渲染的截图**——不是原版 WindTerm 的截图，也不是从原版金图上裁下来的片段；按「整窗」与「组件」两层各守一件事：

- **整窗基线**守「元件在窗口里的位置与是否溢出」——弹窗被挤出屏幕、状态栏被遮住这类问题，只看组件本身看不出来；
- **组件基线**守外观：纯色画布上单独渲染一个组件，背景不含会话树、状态栏与网格，所以改弹窗时比对的就是弹窗本身。

生成方式是可复现的：每个基线由一个夹具（`--demo <名称>`）驱动，夹具直接用语义层处理固定字节流，再拼出快照、窗口、选区，不经过真实 PTY。真实 shell 的提示符、时序与字体回退会让两次运行字节不同，那样的基线活不过一天。

渲染在**隐藏窗口**里完成：带截图参数启动时窗口以不可见方式创建，绘制仍然落在图层上，从渲染后的帧取图。因此跑基线脚本不弹窗、不抢焦点，可以在正在工作的桌面上直接跑。每次运行使用独立的临时配置目录，语言钉死（英文基线固定英文，中文基线单独一张显式给中文），不让基线锚在用户偏好上。

比对是**字节级**的：取 SHA-256 比较，全等才算通过。不设「允许差几个像素」的容差——容差会把「字体抗锯齿变了」与「布局歪了」混成同一类信号。

基线的写入规则：

- **比对路径从不写基线**。只有显式的更新开关才覆盖，且必须在确认差异归因之后执行；
- 基线只读的含义是「不许为了让检查变绿而改基线」。差异先归因：是预期结构变化，还是画错了。归因不清就不更新；
- 成功结果按「二进制哈希 + 脚本哈希 + 基线集合哈希 + 夹具签名」缓存，重复跑同一组合直接复用；缓存只省启动，不改变逐字节判据，更新模式下强制全跑；
- 并行度默认 4，每张图独立配置目录与输出，失败仍按名单顺序汇总，退出码等于失败张数。

组件名单从二进制里取（有一个列出组件的子命令），脚本不另抄一份；只有已冻结基线的组件才进入比对，避免「能出图但还没冻结」的组件制造假红。

重跑与重冻结都只有一个入口（`scripts/screenshot-baseline.sh`）：不带参数比对整窗，`--components` 只比组件，`--all` 两者都跑；加 `--update` 才写基线，`--update --all` 一次重冻两层。并行度用环境变量给（默认 4），调试时设 1 退回逐张执行。

## 9. 已知视觉边界

- **整窗基线绑机器**：字体光栅化、窗口尺寸、系统缩放一变就可能整体漂移。这类漂移的正确处理是重新归因后重冻，而不是放宽判据。
- **基线不含交互中间态**：悬停、按下、拖动过程没有静帧基线，只能在夹具里用「定格」参数近似，真实手感仍靠人工确认。
- **主题只有一套内置文件与七套方案**，没有浅色外壳主题；圆角恒为 0，窗口无阴影。
- **窗口透明度只作用于表面**：字形与描边不跟着变淡，否则整窗会一起糊掉。
- **行高不可单独配置**，字面回落只在槽位层面可见（设置页显示「实际用了谁」），不暴露每个字符的取字结果。

## 10. 设计约束

- 颜色只在 `term-core` 的主题模块定义；`ui/*.rs` 取色一律经外壳适配层，不许写字面量。
- 新增控件表面必须先并入 `CHROME_SCALE` 的灰阶，并有断言守住「中性灰、无饱和蓝铺底、输入框底等于弹窗底」。
- 尺寸改动必须同时更新令牌与基线，不允许只改一处让另一处「看起来差不多」。
- 视觉差异只有两条合法出路：确认是预期变化后重冻基线，或修正实现。第三条「把判据放宽」不存在。
